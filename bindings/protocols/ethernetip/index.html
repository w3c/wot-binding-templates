This initial version of the binding focuses exclusively on tag data access, that is, reading and writing individual controller variables with CIP explicit messaging. Its primary target are Rockwell Automation Logix 5000 family controllers, whose controller-scoped and program-scoped symbolic tags are accessed as described in the Logix 5000 Controllers Data Access programming manual [[1756-PM020]]. Controllers that use PCCC file addresses, such as MicroLogix, SLC 500, and PLC-5, are covered by the addressing and vocabulary rules of this binding, but their encodings are not described here in the same detail. Other EtherNet/IP devices, services, and access methods are expected to be covered by future versions.

This Web of Things (WoT) protocol binding provides guidance for describing assets that leverage the ODVA EtherNet/IP protocol, with an initial focus on Rockwell Automation Logix-family programmable controllers accessed through symbolic tags [[1756-PM020]].

The binding defines:

  • the eip URI scheme used to identify an EtherNet/IP endpoint, including the CIP route path;
  • the controller family that determines the tag address grammar;
  • symbolic tag addressing in WoT Forms;
  • primitive Logix data types;
  • polling behavior, timeouts, and linear value conversion for observed properties;
  • structured tag and User-Defined Type (UDT) descriptions, including nested structures; and
  • mappings between WoT property operations and EtherNet/IP tag access.

This protocol binding is not an ODVA specification, or a Rockwell Automation specification.

This document is a work in progress.

Introduction

EtherNet/IP is an industrial communication protocol that applies the Common Industrial Protocol (CIP) [[CIP]] over standard Ethernet and IP networking. Logix 5000 controllers expose controller-scoped and program-scoped variables as symbolic tags and make them available to external clients through the CIP Read Tag, Read Tag Fragmented, Write Tag, and Write Tag Fragmented services of the Symbol Object, as specified in [[1756-PM020]]. A client reads or writes a tag by identifying the controller and the symbolic tag path, together with enough type information to encode or decode its value.

A Thing Description [[WOT-THING-DESCRIPTION]] can describe these tags as WoT Properties. The Thing Description supplies the endpoint, tag address, supported WoT operations, data type, polling interval, and, for structured tags, the field layout needed by an implementation.

The initial scope of this binding is explicit, non-cyclic tag access, primarily to Rockwell Logix-family controllers and, through the controller family term, to the PCCC-addressed controllers listed in Controller Family. The following topics are outside the initial scope:

  • implicit I/O connections and cyclic producer/consumer data;
  • CIP Safety, CIP Motion, and CIP Sync;
  • device profiles and Assembly Object mappings;
  • arbitrary CIP class, instance, and attribute paths;
  • alarms and events as WoT Event affordances;
  • controller program download or modification; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the eip scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the eip URI scheme;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises;
  4. interprets the declared EtherNet/IP data type correctly; and
  5. interprets structured definitions recursively when eipv:structureDefinition is present.

The primitive type and polling interval use the unprefixed Form members type and pollingTime and consumers implementing this binding MUST accept those names.

URI Scheme and Addressing

Endpoint URI

An EtherNet/IP endpoint is identified by an eip URI:

eip-URI    = "eip://" host [ ":" port ] "/" route-path
route-path = segment *( "," segment )

Where:

  • host is an IPv4 address, IPv6 literal, or DNS name of the controller or communication module;
  • port is optional; when omitted, an implementation uses the EtherNet/IP default explicit-messaging port configured by that implementation;
  • route-path is the CIP route from the communication module to the controller, expressed as the comma-separated sequence of port and address segments used by CIP connection paths. When the route path is omitted, an implementation MUST assume 1,0, which is the backplane port followed by slot 0.

The route path is part of the interoperable profile because it is required to open a connection. The value 1,0 only addresses a controller in slot 0 of the chassis that the communication module belongs to. A ControlLogix controller in another slot, a CompactLogix controller, or a controller reached through a further Ethernet module needs a different route, and a Thing Description that omits it is not portable between Consumers. Route paths MAY contain several hops, including Ethernet hops with embedded IP addresses.

Endpoint Meaning
eip://192.168.0.10/1,0 Controller in slot 0, reached over the backplane of the addressed module
eip://192.168.0.10/1,3 Controller in slot 3 of the same chassis
eip://192.168.0.10/1,4,2,192.168.1.20,1,0 Controller in slot 0 of a remote chassis, reached through an Ethernet module in slot 4

A Thing Description SHOULD place the controller endpoint, including the route path, in base and use relative tag references in individual Forms. 

{
  "base": "eip://192.168.0.10/1,0/",
  "eipv:controller": "ControlLogix"
}

Controller Family

Controllers that speak EtherNet/IP do not share a single tag address grammar or CIP encoding. Logix 5000 controllers use symbolic tags [[1756-PM020]], while MicroLogix, SLC 500, and PLC-5 controllers use file-style addresses such as N7:1 or B3:0/3 carried over PCCC, and Micro800 and third-party controllers differ again. A Consumer therefore MUST know the controller family before it can encode a request, which is why the family is part of the interoperable profile.

A Thing Description carrying eip Forms SHOULD declare the controller family at the top level with eipv:controller. When the term is absent, an implementation MUST assume ControlLogix. The value is one of:

Value Address grammar
ControlLogix Logix symbolic tags
CompactLogix Logix symbolic tags
Micro800 Logix symbolic tags
MicroLogix PCCC file addresses
SLC500 PCCC file addresses
PLC5 PCCC file addresses
Omron Omron NJ/NX symbolic tags

The symbolic addressing rules in Symbolic Tag Reference apply to the controller families that use Logix symbolic tags. For the families that use PCCC file addresses, the tag-path is the file address as written in the controller programming software, for example N7:1 for an integer file element or B3:0/3 for a bit. Percent-encoding applies as described in Reserved Characters.

Symbolic Tag Reference

The resolved Form target identifies a Logix symbolic tag. The initial binding uses the following shape:

eip-tag-URI = eip-URI "/" tag-path [ "?offset=" byte-offset ]

The tag-path is the controller's symbolic tag expression, using the symbolic addressing syntax defined for Logix 5000 controllers in [[1756-PM020]]. The following forms are supported:

Form Meaning Example
TagName Controller-scoped tag MotorSpeed
Program:ProgramName.TagName Program-scoped tag Program:Packaging.Counter
TagName.MemberName Member of a structured tag or UDT, repeated for nested structures Mixer.Status.Running
TagName[index] Array element; one subscript per dimension, separated by commas, for up to three dimensions Recipe[3].SetPoint, Grid[1,2]
TagName.bit Bit of an integer tag StatusWord.3

Tag names are case-insensitive in the controller, but an implementation MUST transmit the tag path as written, because the ANSI Extended Symbol Segments of the CIP request are built directly from the symbolic elements of the tag path. The tag path MUST be percent-decoded first, see Reserved Characters. 

MotorSpeed
Program:Packaging.Counter
Mixer.Status.Running
Recipe%5B3%5D.SetPoint

The tag-path MUST be the fully qualified tag path, so that array elements, structure members, and bits are selected by the syntax above rather than by a query component. This is the form that both symbolic-tag implementations surveyed for this binding execute directly.

The optional offset query parameter selects a raw byte offset into the value of the addressed tag, for the cases where a tag has no member syntax for the value of interest, such as the connection status tags of a communication module. Its value is a non-negative integer counted in bytes, not in array elements, and an implementation MUST reject a Form whose offset exceeds the length of the tag. Authors SHOULD NOT use it for array or member access.

Earlier drafts allowed a bare ?N query component. It was ambiguous, because it was specified as an array element index but implemented as a byte offset, so it has been replaced by the explicit ?offset= form.

Reading a range of array elements with a single Form, such as the first four elements of an array, is out of scope for this version of the binding. A Form addresses either a single element or a whole tag. 

{
  "href": "MotorSpeed"
}

When the Thing Description contains "base": "eip://192.168.0.10/1,0/", the resolved target is eip://192.168.0.10/1,0/MotorSpeed.

Reserved Characters

Logix symbolic tag expressions can contain characters that are reserved in URIs [[RFC3986]], in particular : in program-scoped tag names such as Program:Packaging.Counter and [ and ] in array subscripts such as Recipe[3].SetPoint.

Authors MUST percent-encode any character of a tag path that is not allowed in the path component of a URI reference, and in particular MUST percent-encode [ as %5B, ] as %5D, ? as %3F, and # as %23. Because the tag path is a single path segment, / MUST be percent-encoded as %2F when it is part of a tag name.

The characters : and . are allowed in a non-initial path segment and therefore need not be percent-encoded. An implementation MUST percent-decode the tag path before it is used as a symbolic tag expression. 

eip://192.168.0.10/1,0/Recipe%5B3%5D.SetPoint

EtherNet/IP Vocabulary

The examples use the prefix eipv for the provisional namespace. The prefix intentionally differs from the eip URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "eipv": "https://www.w3.org/2026/wot/eip"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Thing Terms

Vocabulary term Description Assignment Value
eipv:controller Controller family that determines the tag address grammar and the CIP encoding, see Controller Family. optional, default ControlLogix ControlLogix, CompactLogix, MicroLogix, SLC500, PLC5, Micro800, or Omron

Form Terms

Vocabulary term Description Assignment Value
href Symbolic tag reference, resolved against base when relative. required URI reference
op WoT operations supported by the Form. required Array containing supported operations
type EtherNet/IP/Logix primitive type used to encode and decode the tag value. required for primitive tags One value from Primitive Data Types
pollingTime Requested polling interval for observeproperty, in milliseconds. optional Non-negative integer
eipv:timeout Maximum time to wait for the controller response, in milliseconds. optional Non-negative integer
eipv:scale Factor applied to the controller value to obtain the application-facing value, see Value Conversion. optional, default 1 Number
eipv:offset Summand applied after eipv:scale, see Value Conversion. optional, default 0 Number
eipv:structureDefinition Recursive definition of a structured Logix tag or UDT. optional Object defined in Structured Type Definition

A Form MUST NOT contain both a primitive type and an eipv:structureDefinition. Primitive tags use type, while structured tags either use eipv:structureDefinition or carry neither term and are decoded from the definition that the Consumer obtains from the controller, see Structure Definition Precedence.

Value Conversion

Logix tags usually hold engineering values, so no conversion is needed. MicroLogix and SLC integer files and many Logix programs nevertheless keep scaled integers, for example a temperature in tenths of a degree in an eipv:INT tag. A Form MAY therefore carry eipv:scale and eipv:offset.

When reading, a Consumer computes the application-facing value as value = raw × eipv:scale + eipv:offset, and when writing it applies the inverse, raw = (value − eipv:offset) / eipv:scale, rounding to the nearest representable value of the declared type. These are the same two terms, with the same semantics, as in the Modbus binding, so that an author learns one rule for both. 

{
  "href": "TankTemp",
  "op": ["readproperty"],
  "type": "eipv:INT",
  "eipv:scale": 0.1
}

Primitive Data Types

The binding identifies Logix primitive types with terms from the EtherNet/IP vocabulary. The type names are the CIP and Logix type names defined in [[1756-PM020]]; they are not XML Schema datatypes. The second column gives the CIP data type code that a controller returns in the response of a Read Tag service and that a client sends in a Write Tag service. The third column lists the closest XML Schema built-in datatype [[XMLSCHEMA11-2]] for authors who need one, and the fourth column gives the recommended WoT Data Schema.

Value Logix type and CIP type code Closest XML Schema datatype WoT Data Schema recommendation
eipv:BOOL Boolean, 0xC1 xsd:boolean boolean
eipv:SINT Signed 8-bit integer, 0xC2 xsd:byte integer, minimum -128, maximum 127
eipv:INT Signed 16-bit integer, 0xC3 xsd:short integer, minimum -32768, maximum 32767
eipv:DINT Signed 32-bit integer, 0xC4 xsd:int integer, minimum -2147483648, maximum 2147483647
eipv:LINT Signed 64-bit integer, 0xC5 xsd:long integer
eipv:USINT Unsigned 8-bit integer, 0xC6 xsd:unsignedByte integer, minimum 0, maximum 255
eipv:UINT Unsigned 16-bit integer, 0xC7 xsd:unsignedShort integer, minimum 0, maximum 65535
eipv:UDINT Unsigned 32-bit integer, 0xC8 xsd:unsignedInt integer, minimum 0
eipv:ULINT Unsigned 64-bit integer, 0xC9 xsd:unsignedLong integer, minimum 0
eipv:REAL IEEE 754 single-precision floating point, 0xCA xsd:float number
eipv:LREAL IEEE 754 double-precision floating point, 0xCB xsd:double number
eipv:BYTE 8-bit string, 0xD1 xsd:unsignedByte integer, minimum 0, maximum 255
eipv:WORD 16-bit string, 0xD2 xsd:unsignedShort integer, minimum 0, maximum 65535
eipv:DWORD 32-bit string, 0xD3 xsd:unsignedInt integer, minimum 0
eipv:LWORD 64-bit string, 0xD4 xsd:unsignedLong integer, minimum 0
eipv:STRING Predefined Logix STRING structure, transferred as a structure (0xA0) xsd:string string

The bit-string types eipv:BYTE, eipv:WORD, eipv:DWORD, and eipv:LWORD hold collections of bits rather than numbers; they are the storage behind BOOL arrays and appear in status words of Add-On Instructions. They are transferred with the same width as the corresponding unsigned integer type, so a Consumer that has no distinct representation for bit strings MAY expose them as unsigned integers.

All primitive values are transferred in little-endian byte order. A eipv:BOOL value is transferred in a single byte whose least significant bit carries the value, while a BOOL member of a structure is packed into a bit of an enclosing byte or word, see Structured Type Definition.

The predefined STRING type is a structure consisting of a DINT member LEN that holds the number of valid characters, followed by a SINT array member DATA that holds the characters [[1756-PM020]]. An implementation decoding eipv:STRING MUST use LEN to determine the number of characters and MUST set LEN when encoding. Controllers also support user-defined string types with a different DATA length; those follow the same layout.

Implementations MUST reject an unsupported type rather than silently decode it as another type.

Structured Type Definition

eipv:structureDefinition is an optional description of a Logix UDT and has the following members:

Member Description Assignment Value
typeName Controller-defined name of the UDT. required string
fields Ordered field definitions. required array of field-definition objects

Each field-definition object has the following members:

Member Description Assignment Value
name Field name in the UDT. required string
type Primitive type from Primitive Data Types. required for primitive fields string
offset Byte offset of the field in the encoded structure. required non-negative integer
bitOffset Bit position of a eipv:BOOL field inside the byte identified by offset. required for eipv:BOOL fields integer from 0 to 7
description Human-readable description of the field. optional string
eipv:structureDefinition Nested UDT definition. required for nested UDT fields structure-definition object

A field MUST use either type for a primitive field or eipv:structureDefinition for a nested UDT field. A consumer MUST process nested structure definitions recursively.

The offsets MUST describe the layout that the controller uses on the wire, as documented in [[1756-PM020]]. In particular:

  • members are aligned on a boundary that matches their size, so a DINT or REAL member starts on a 4-byte boundary and a LINT or LREAL member starts on an 8-byte boundary, which means that padding bytes can appear between members;
  • consecutive BOOL members are packed into the bits of a single byte or word, so that offset alone does not identify such a member and bitOffset MUST be given;
  • a nested structure member starts at the alignment required by its own largest member, and its field offsets are relative to the start of that nested structure; and
  • the overall structure length is padded to its alignment.

Because the controller reports this layout through its template and symbol metadata, authors SHOULD generate the structure definition from the controller rather than by hand. 

{
  "eipv:structureDefinition": {
    "typeName": "MotorStatus",
    "fields": [
      {
        "name": "Running",
        "type": "eipv:BOOL",
        "offset": 0,
        "bitOffset": 0,
        "description": "Indicates whether the motor is running"
      },
      {
        "name": "Speed",
        "type": "eipv:REAL",
        "offset": 4,
        "description": "Actual motor speed"
      }
    ]
  }
}

Structure Definition Precedence

Logix controllers are browsable: a Consumer can read the tag list and the template of a UDT from the controller and derive the layout at runtime. An embedded eipv:structureDefinition can go stale after a program download and then decodes wrong values silently, with no error for the application to catch.

A Consumer that can obtain the definition from the controller SHOULD prefer the live definition over eipv:structureDefinition, and SHOULD warn when the two differ. The embedded definition is intended for offline authoring and for targets that cannot be browsed.

A Form addressing a structured tag MAY therefore omit eipv:structureDefinition and name the tag only. A Consumer that can neither browse the controller nor decode a whole structure MUST use Forms whose href addresses individual members, for example LineState.Drive.Current; member paths are the one form of UDT access that every surveyed implementation can execute.

Operation Mappings

Default Mappings

WoT operation EtherNet/IP behavior Requirements
readproperty Send a CIP Read Tag service (0x4C), or a Read Tag Fragmented service (0x52) when the value does not fit into a single reply, to the symbolic tag and decode the returned value according to type or eipv:structureDefinition [[1756-PM020]]. The Form MUST identify a readable tag.
writeproperty Encode the supplied value according to type or eipv:structureDefinition and send it with a CIP Write Tag service (0x4D), or a Write Tag Fragmented service (0x53) when the value does not fit into a single request [[1756-PM020]]. The property MUST NOT be declared readOnly: true.
observeproperty Repeatedly read the tag and notify the Consumer when a sample is available or its value changes, according to implementation behavior. observable SHOULD be true; pollingTime controls the requested interval.

The initial binding does not define a native EtherNet/IP subscription mechanism. An implementation MAY realize observeproperty by polling. It SHOULD use pollingTime when supplied and MAY enforce a minimum interval to protect the controller and network. An implementation MAY combine the reads of several Forms of the same endpoint into a single CIP Multiple Service Packet request (0x0A) [[1756-PM020]] to reduce the load on the controller.

Action and Event Mappings

No default mapping is defined for:

  • invokeaction;
  • subscribeevent;
  • unsubscribeevent; or
  • WoT Event affordances.

A Thing Description conforming to the profile MUST NOT advertise those operations on an eip Form unless it also declares and documents an additional binding extension.

Payload Mapping

Primitive Values

Primitive values are represented at the WoT Consumer boundary as the JSON value compatible with the Property's WoT Data Schema. The binding implementation is responsible for converting between that value and the corresponding Logix wire representation.

A consumer MUST use both the WoT Data Schema and the Form's Logix type. The WoT Data Schema describes the application-facing value, while the Form term identifies the controller representation.

Structured Values

A structured Logix tag is represented to the WoT Consumer as a JSON object. Field names in the object correspond to the name members in eipv:structureDefinition.fields. 

{
  "Running": true,
  "Speed": 1450.5
}

The binding implementation uses each field's offset, its bitOffset for packed eipv:BOOL members, and its primitive or nested type definition to decode and encode the controller value. When writing a structured tag, the implementation MUST preserve the bytes that no field covers, such as alignment padding, which requires reading the tag before writing it back.

Arrays

Array elements are exposed through the Form href, using the Logix subscript syntax of [[1756-PM020]], which supports up to three dimensions. A Form addressing a single element is decoded like a scalar of the same type.

This binding does not define a complete interoperable array model, including dimensions, bounds, bulk reads of multiple elements, or slicing. An implementation that reads more than one element at a time does so with the element count of the CIP Read Tag service and the offset of the Read Tag Fragmented service [[1756-PM020]], which this version of the binding does not describe in the Thing Description.

Security Considerations

EtherNet/IP controllers and communication modules differ in the security services they expose. A Thing Description MUST accurately describe the security applied to the interaction endpoint.

ODVA specifies security services for CIP and EtherNet/IP in CIP Security [[CIP-SECURITY]], published as Volume 8 of the CIP Networks Library. The following profiles are relevant to explicit messaging as used by this binding:

  • the EtherNet/IP Confidentiality Profile, which protects explicit messaging with TLS (for TCP) and DTLS (for UDP), providing endpoint authentication, message integrity, and encryption;
  • the EtherNet/IP IEEE 802.1X Profile, which provides device-level network access control and device identity;
  • the CIP Authorization Profile, which uses JSON Web Tokens to authorize access to CIP objects and services; and
  • the CIP User Authentication Profile, which authenticates users and issues the tokens consumed by the CIP Authorization Profile.

These services are implemented by shipping products, including Rockwell Automation Logix-family controllers and their EtherNet/IP communication modules. Support depends on the product family and firmware revision, so an implementation cannot assume that a given controller offers them.

When an endpoint is protected by the EtherNet/IP Confidentiality Profile, the Thing Description SHOULD describe the corresponding credentials with a WoT security scheme that matches the deployed configuration, for example a certificate-based scheme for TLS mutual authentication, or a token-based scheme when the CIP Authorization Profile is used. The examples in this document use nosec only because they describe controllers that are deployed without CIP Security; nosec MUST NOT be used to describe a CIP Security-protected endpoint.

A binding implementation MUST NOT infer that nosec authorizes access. Authorization remains a deployment responsibility.

This binding does not yet define vocabulary terms for selecting CIP Security profiles or for carrying profile-specific parameters in a Form. The mapping between the CIP Security profiles listed above and the WoT security schemes is expected to be refined as implementation experience with CIP Security-enabled controllers is collected.

Implementation Notes

This binding was compared against two implementations built on the open-source libplctag library, the OPC Foundation's UA Edge Translator and DIME, and against the eip, logix, and ab-eth drivers of Apache PLC4X. The UA Edge Translator implementation currently:

  • registers the protocol scheme as eip;
  • identifies its provisional WoT binding URI as https://www.w3.org/2019/wot/eip;
  • accesses symbolic tags with the CIP Read Tag, Read Tag Fragmented, Write Tag, and Write Tag Fragmented services described in [[1756-PM020]];
  • hardcodes the route path 1,0 and the ControlLogix controller family, and therefore needs to adopt the base route path and eipv:controller of this binding to reach controllers in other slots, chassis, or families;
  • supports controller discovery through the EtherNet/IP ListIdentity broadcast; and
  • reads controller tag metadata to generate Property affordances.

Apache PLC4X carries the route as a connection option and selects the controller family by driver, addresses array elements and UDT members with qualified tag paths, has no tag browsing or whole-UDT decoding, and exposes a request timeout. The addressing and vocabulary decisions of this binding follow that shared behavior.

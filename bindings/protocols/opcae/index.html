This Web of Things (WoT) protocol binding describes how a Thing Description exposes the alarms and events of an OPC Alarms and Events (OPC A&E) server [[OPC-AE]], one of the COM-based OPC Classic specifications, and how those alarms and events are made available as OPC UA Alarms and Conditions [[OPC-UA-PART9]].

The binding is limited to local COM: the Consumer and the OPC A&E server run on the same computer. Remote access through Distributed COM (DCOM) is not supported, see COM Only.

The binding defines:

  • the opcae URI scheme used to identify a local OPC A&E server and its event sources;
  • event subscriptions for WoT Events, filtered by event type, category, severity, area, and source;
  • a JSON payload for event notifications whose members are the fields of the corresponding OPC UA event types;
  • the exposure of these events as OPC UA events and conditions, and the mapping of the OPC UA condition methods, such as Acknowledge and ConditionRefresh, onto the OPC A&E interfaces; and
  • mappings between WoT operations and the OPC A&E interfaces.

This protocol binding is not an OPC Foundation specification.

This document is a work in progress.

This initial version of the binding covers event subscriptions and condition acknowledgement of OPC A&E 1.0 and 1.10 servers through local COM; DCOM is not covered. It shares the URI layout, the COM-only scope, and the security considerations of the companion OPC DA Binding [[WOT-OPCDA-BINDING]] and OPC HDA Binding.

Introduction

OPC Alarms and Events is the OPC Classic specification for alarms and event notifications. An OPC A&E server is a COM server that runs on a Microsoft Windows computer and reports events detected by control systems, operator stations, or the server itself. Clients on the same computer reach the server through COM. The OPC A&E specification also allows remote clients through Distributed COM (DCOM) [[MS-DCOM]], which this binding does not support.

OPC A&E distinguishes three types of events:

  • simple events, such as a device failure or a batch completion;
  • tracking events, which report an action of an operator or another actor, such as a setpoint change; and
  • condition-related events, which report a change of a condition, such as LevelAlarm, of a source, such as Plant1.Tank3.Level. A condition is active or inactive, acknowledged or unacknowledged, and enabled or disabled, and it has subconditions, such as HI and HI HI.

Every event has a category, a server-defined classification, and a severity from 1 to 1000. Sources are organized in a hierarchy of process areas. A client creates an event subscription, sets a filter on it, and receives the matching events through a callback.

The OPC A&E condition model was carried over into OPC UA Alarms and Conditions [[OPC-UA-PART9]]. This binding therefore describes an OPC A&E event stream as a WoT Event, and represents every event notification with the fields of the OPC UA event type that corresponds to the OPC A&E event, such as ExclusiveLevelAlarmType for a level alarm. Condition management, such as acknowledging an alarm, is made through OPC UA instead of through WoT Actions: a Consumer that exposes the WoT Event as OPC UA events, for example a WoT gateway that is also an OPC UA server, reports the conditions as OPC UA conditions and maps the OPC UA condition methods onto the OPC A&E methods, as specified in OPC UA Alarms and Conditions. This keeps the Thing Description simple and gives OPC UA clients the same view of the alarms that OPC UA wrappers of OPC A&E servers provide.

The following topics are outside the initial scope:

  • remote access through DCOM, see COM Only;
  • the OPC XML web service specifications;
  • condition management through WoT Actions and condition states as WoT Properties, including GetConditionState and the enabling and disabling of conditions by process area;
  • event server configuration, such as defining conditions;
  • translating event attributes to OPC DA item IDs with TranslateToItemIDs; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the opcae scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the opcae URI scheme and rejects URIs that do not address the local computer;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises;
  4. converts event notifications into the JSON payload specified; and
  5. when it exposes Events as OPC UA events, maps the OPC UA event types and condition methods as specified in OPC UA Alarms and Conditions.

The interoperable profile of this binding is the subset of its URI components, vocabulary terms, and behaviors that every conforming Consumer MUST support. A Thing Description that uses only the interoperable profile therefore works with every conforming Consumer, while anything outside it, such as a binding extension, is only understood by Consumers that implement that extension. Unless a section states otherwise, all URI components, vocabulary terms, and operation mappings defined normatively in this document belong to the interoperable profile.

OPC Classic Background

OPC Data Access (DA), OPC Historical Data Access (HDA), and OPC A&E are known together as OPC Classic. They share the following foundations, which this binding relies on:

  • A server is a COM class, identified by a class identifier (CLSID) and usually also by a programmatic identifier (ProgID) such as Vendor.OPCAEServer.1. A client creates the server object with CoCreateInstance. Most OPC servers are out-of-process servers, that is, separate executables that COM starts on demand.
  • OPC A&E servers register themselves in the component category CATID_OPCAEServer10, which lets a client list the OPC A&E servers installed on the computer.
  • All OPC Classic servers implement IOPCCommon and announce an orderly shutdown through the IOPCShutdown callback interface [[OPC-COMMON]].
  • Event notifications are delivered over COM connection points, so the server calls back into the client process.

COM Only

This binding only covers access to an OPC A&E server through local COM. The Consumer MUST run on the same computer as the server. Access to a server on another computer through DCOM [[MS-DCOM]] is outside the scope of this binding, and a Consumer MUST NOT use DCOM to realize an opcae Form.

This is a deliberate limitation, shared with the companion OPC DA and OPC HDA bindings. DCOM is generally not used in industry today because of its complex firewall and permission configuration and its security issues; remote access to OPC Classic servers is instead commonly provided by OPC UA wrappers or tunnelling products that run next to the server. The rationale is described in more detail in [[WOT-OPCDA-BINDING]].

A Thing Description that is consumed on another computer therefore describes the alarms and events through such a gateway with a different protocol binding, or it is used by a Consumer, such as a WoT gateway, that runs on the server computer and exposes the events again through a network protocol, such as OPC UA as described in OPC UA Alarms and Conditions.

URI Scheme and Addressing

Server URI

An OPC A&E server is identified by an opcae URI:

opcae-URI = "opcae://localhost/" server-id "/"
server-id = progid / clsid

The host, which is always localhost, and the components progid and clsid are defined exactly as for the opcda URI in [[WOT-OPCDA-BINDING]]. In particular, a Consumer MUST reject an opcae URI with any other host, the URI MUST NOT contain a port, user information, query, or fragment, and the base of a Thing Description MUST end with /. 

{
  "base": "opcae://localhost/Vendor.OPCAEServer.1/"
}

Source Reference

The resolved Form target identifies the server, or an event source of the server:

opcae-source-URI = opcae-URI [ source-name ]

The source-name is the fully qualified name of a source, as reported in event notifications, for example Plant1.Tank3.Level. The name is a single path segment and is percent-encoded and decoded as specified for item IDs in [[WOT-OPCDA-BINDING]]: /, ?, #, %, [, ], \, and space MUST be percent-encoded, and a relative href whose name contains a colon MUST start with ./ or percent-encode the colon. An implementation MUST pass the percent-decoded name to the server exactly as written.

When the resolved target has no source-name, that is, when it equals the server URI, the Form addresses the server as a whole. Such a Form is typically written with the href "./".

OPC A&E Vocabulary

The examples use the prefix opcaev for the provisional namespace. The prefix intentionally differs from the opcae URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "opcaev": "https://www.w3.org/2026/wot/opcae"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Operation Mappings

Event Mappings

WoT operation OPC A&E mapping
subscribeevent
  1. Call IOPCEventServer::CreateEventSubscription with bActive set to FALSE, opcaev:bufferTime, and opcaev:maxSize.
  2. Call IOPCEventSubscriptionMgt::SetFilter with the filter given by the Form terms, see below.
  3. For every element of opcaev:returnedAttributes, call IOPCEventSubscriptionMgt::SelectReturnedAttributes.
  4. When opcaev:keepAlive is present, call IOPCEventSubscriptionMgt2::SetKeepAlive.
  5. Register an IOPCEventSink through the subscription's IConnectionPointContainer, and activate the subscription with IOPCEventSubscriptionMgt::SetState.
  6. When opcaev:refresh is true, call IOPCEventSubscriptionMgt::Refresh.
Every event of every IOPCEventSink::OnEvent callback for the subscription is a notification whose data is an event notification.
unsubscribeevent Unregister the IOPCEventSink and release the subscription object. When a refresh is in progress, the Consumer SHOULD first call IOPCEventSubscriptionMgt::CancelRefresh.

The filter passed to SetFilter is derived as follows:

  • the event type is the combination of OPC_SIMPLE_EVENT (1), OPC_TRACKING_EVENT (2), and OPC_CONDITION_EVENT (4) for the values of opcaev:eventTypes, or OPC_ALL_EVENTS (7) when the term is absent;
  • the categories, areas, and severities are those of opcaev:categories, opcaev:areas, opcaev:lowSeverity, and opcaev:highSeverity; and
  • the sources are those of opcaev:sources, or, when the resolved target contains a source-name, that single source. A Form whose target contains a source-name MUST NOT carry opcaev:sources.

A server reports the filters it supports with IOPCEventServer::QueryAvailableFilters. A Consumer MUST fail the subscription when the Form requests a filter that the server does not support, rather than silently deliver unfiltered events.

The server MAY revise the buffer time, the maximum size, and the keep-alive time, in which case it returns OPC_S_INVALIDBUFFERTIME, OPC_S_INVALIDMAXSIZE, or OPC_S_INVALIDKEEPALIVETIME. A Consumer MUST accept revised values and MAY warn about them. A Consumer MUST NOT deliver an empty keep-alive callback as a notification; it MAY use the absence of keep-alive callbacks to detect a broken connection.

Refresh

Event subscriptions only report changes. A Consumer that needs the current alarm situation, for example to fill an alarm list, sets opcaev:refresh to true. The server then sends a condition-related event for every condition that is active, or inactive and unacknowledged, and that matches the filter. These events are delivered as notifications like any other event; their Retain member is true, so a Consumer adds them to its alarm list. A Consumer that exposes the Event through OPC UA also uses Refresh to implement ConditionRefresh.

Server Status

A Form whose resolved target equals the server URI and that contains the readproperty operation addresses the server status. readproperty calls IOPCEventServer::GetStatus and returns an object with the members state, startTime, currentTime, lastUpdateTime, version, and vendorInfo, converted from the OPCEVENTSERVERSTATUS fields as defined for the OPC DA server status in [[WOT-OPCDA-BINDING]]. The values of state are running, failed, noConfig, suspended, test, and commFault, for OPCAE_STATUS_RUNNING to OPCAE_STATUS_COMM_FAULT.

A Form whose resolved target contains a source-name MUST NOT contain readproperty. No default mapping is defined for observeproperty, unobserveproperty, or writeproperty.

Server Shutdown

A Consumer SHOULD register an IOPCShutdown callback with the server [[OPC-COMMON]]. When the server calls ShutdownRequest, the Consumer MUST release all references to the server, MUST end all active subscriptions with an error that includes the reason supplied by the server, and MAY reconnect later. After reconnecting, the Consumer SHOULD request a refresh, because events that occurred in the meantime are lost.

Action Mappings

No default mapping is defined for invokeaction or for WoT Action affordances. A Thing Description conforming to the profile MUST NOT advertise that operation on an opcae Form unless it also declares and documents an additional binding extension. Conditions are acknowledged, enabled, and disabled through OPC UA, see Condition Methods.

Error Handling

OPC A&E reports errors as HRESULT codes. A Consumer MUST report a failed operation to the application when the call fails. The following codes are particularly relevant:

Code Meaning Consumer behavior
E_INVALIDARG A parameter is invalid, for example an unknown category or an inverted severity range in the filter, or an unknown area or source. Fail the operation.
OPC_E_BUSY A refresh is already in progress for the subscription. Fail the subscription, or retry the refresh later.
OPC_S_INVALIDBUFFERTIME, OPC_S_INVALIDMAXSIZE, OPC_S_INVALIDKEEPALIVETIME The server revised a subscription parameter. Succeed, and MAY warn.

The OPC UA status codes returned for the OPC UA condition methods are specified in Condition Methods.

A member whose value is not available is omitted.

Event Attributes

The attributes selected with opcaev:returnedAttributes are returned in pEventAttributes, in the order of the identifiers in opcaev:attributeIds for the category of the event. Each attribute is represented as a member of the event notification, named by the description of the attribute reported by IOPCEventServer::QueryEventAttributes, with the value converted as described for OPC DA item values in [[WOT-OPCDA-BINDING]]. The following rules apply:

  • the first attribute whose description is ACK COMMENT is represented as the Comment member of a condition-related event;
  • an attribute whose description equals the name of a member defined in Event Notifications is omitted; and
  • an attribute whose value is VT_EMPTY is omitted.

When the event is exposed through OPC UA, every other attribute becomes an event field of the event type with that browse name, in a namespace of the Consumer.

OPC UA Alarms and Conditions

This section applies to a Consumer that exposes Events with opcae Forms as OPC UA events, for example a WoT gateway that is also an OPC UA server. It specifies how the events and conditions are represented in OPC UA [[OPC-UA-PART9]], and how the OPC UA condition methods are mapped onto the OPC A&E interfaces of the server addressed by the Form.

Event Notifiers

For every such Event, the Consumer MUST:

  • expose an Object, typically the Object that represents the Thing, whose EventNotifier attribute has SubscribeToEvents set, and that is the target of a HasNotifier reference from the Server Object, directly or through other notifiers;
  • create the OPC A&E event subscription, as for subscribeevent, while at least one OPC UA monitored item for events exists on that Object or on one of its notifiers;
  • report every event notification as an OPC UA event of the event type selected in Event Types, with the fields of Event Notifications; and
  • set the SourceNode field to the NodeId of the Node that represents the source, when the Consumer exposes one, and to the NodeId of the notifier Object otherwise.

The Consumer evaluates the EventFilter of each OPC UA monitored item on the converted events. It MAY narrow the OPC A&E filter with the event types and severities of a WhereClause, but it MUST NOT widen it beyond the filter given by the Form.

Event Types

The OPC UA event type of an event is selected by its OPC A&E event type, the description of its category, and the name of its condition, as follows. The category descriptions and condition names are the recommended names of [[OPC-AE]]. They are compared without regard to case, and a space in a recommended name also matches an underscore or nothing, so that PV LEVEL, PV_LEVEL, and pvlevel all match PVLEVEL. The first row that matches applies.

Event type Category description Condition name OPC UA event type
simple Device Failure - DeviceFailureEventType
simple System Message - SystemEventType
simple any other - BaseEventType
tracking any - AuditEventType
condition Level PVLEVEL, SPLEVEL ExclusiveLevelAlarmType
condition Level HI HI, HI, LO, LO LO NonExclusiveLevelAlarmType
condition Level any other LimitAlarmType
condition Deviation any NonExclusiveDeviationAlarmType
condition Discrete CFN OffNormalAlarmType
condition Discrete TRIP TripAlarmType
condition Discrete any other DiscreteAlarmType
condition any other any AlarmConditionType

A Consumer MAY define a subtype of the selected OPC UA event type for every category, or for every category and condition, and report the events with that subtype, for example to declare the event attributes of the category as fields of the subtype. The EventType member of the event notification is always the browse name of the type selected in the table.

Conditions

Every pair of a source and a condition name identifies an OPC A&E condition, which the Consumer represents as an OPC UA condition with the following properties:

  • the ConditionId, that is, the NodeId of the condition, is derived from the source and the condition name, and is the same for all events of the condition;
  • the ConditionClassId is BaseConditionClassType, unless the Consumer defines a condition class for the category, and the ConditionClassName is the description of the category;
  • the BranchId is null, because OPC A&E has no condition branches;
  • the EventId MUST allow the Consumer to recover the source, the condition name, the exact ftActiveTime, and the dwCookie of the event, which AckCondition requires. The Consumer MAY encode them in the EventId, as the OPC UA COM wrappers of the OPC Foundation do, or keep them in a table indexed by the EventId; and
  • the optional ConfirmedState, ShelvingState, SuppressedState, and OutOfServiceState are not exposed, because OPC A&E has no counterpart for them.

A Consumer MAY also expose the conditions as Nodes in its address space, referenced from the Node of their source with HasCondition. The values of such a Node are those of the most recent event of the condition.

Limit States

For limit and deviation alarms, the name of the active subcondition, or, when that name is not one of the names below, the name of the condition, selects the limit that was exceeded. The names are compared as in Event Types.

Name LimitState of exclusive alarms State of non-exclusive alarms
HI HI HighHigh HighHighState
HI, DV HI High HighState
LO, DV LO Low LowState
LO LO LowLow LowLowState

For an exclusive alarm, LimitState is omitted when the condition is inactive. For a non-exclusive alarm, the Id of the selected state is the active state of the condition.

Condition Methods

The Consumer MUST map the OPC UA methods of the conditions as follows. The ObjectId of each call is the ConditionId of the condition.

OPC UA method OPC A&E mapping
Acknowledge Recover the source, the condition name, the active time, and the cookie from the EventId argument, and call IOPCEventServer::AckCondition for that single condition, with the text of the Comment argument as szComment, and with the acknowledger ID described below.
Enable, Disable OPC A&E can only enable and disable all conditions of a source or a process area together. When IOPCEventServer::QuerySourceConditions reports the condition as the only condition of its source, the Consumer MAY call EnableConditionBySource or DisableConditionBySource for that source. Otherwise, it MUST return BadNotSupported, rather than enable or disable other conditions as well.
AddComment OPC A&E has no comments outside acknowledgements. The Consumer MUST return BadNotSupported.
ConditionRefresh, ConditionRefresh2 See Condition Refresh.

The acknowledger ID passed to AckCondition MUST NOT be empty. It SHOULD identify the OPC UA user of the session that calls Acknowledge, for example by the display name of its user identity token. For an anonymous session, the Consumer SHOULD use a configured name that identifies the Consumer.

The method results are converted as follows. Enable and Disable return BadConditionAlreadyEnabled and BadConditionAlreadyDisabled when the most recent event of the condition already reports the requested state, without calling the server.

OPC A&E result OPC UA status code
S_OK Good
OPC_S_ALREADYACKED BadConditionBranchAlreadyAcked
OPC_E_INVALIDTIME, E_INVALIDARG of AckCondition, or an EventId that the Consumer cannot resolve BadEventIdUnknown
E_INVALIDARG of EnableConditionBySource or DisableConditionBySource BadNodeIdUnknown
any other error BadUnexpectedError

A successful method call has no immediate effect on the condition Node. The OPC A&E server reports the new state of the condition with a condition-related event, which the Consumer reports as an OPC UA event like any other.

Condition Refresh

For ConditionRefresh and ConditionRefresh2, the Consumer MUST, for every OPC A&E event subscription that backs an affected monitored item:

  1. report a RefreshStartEventType event to the monitored item;
  2. call IOPCEventSubscriptionMgt::Refresh, and report every event of the refresh callbacks, whose bRefresh parameter is TRUE, to the monitored item only; and
  3. report a RefreshEndEventType event after the callback whose bLastRefresh parameter is TRUE.

When the server returns OPC_E_BUSY, the Consumer MUST either wait for the refresh in progress to complete and start a new one, or return BadRefreshInProgress. A Consumer MAY cancel a refresh that does not complete in time with IOPCEventSubscriptionMgt::CancelRefresh, in which case it still reports the RefreshEndEventType event.

Generating Thing Descriptions

OPC A&E servers describe their event space. A tool that generates a Thing Description can use the following methods of IOPCEventServer:

  • QueryEventCategories lists the categories of each event type, which give values for opcaev:categories and, together with QueryConditionNames, the OPC UA event types of Event Types that the Data Schema of an Event describes;
  • QueryEventAttributes lists the attributes of each category with their descriptions and data types, which give opcaev:returnedAttributes and the members of the Data Schema for event attributes;
  • CreateAreaBrowser walks the process area hierarchy, which gives values for opcaev:areas; and
  • QueryAvailableFilters tells which filter terms the server supports.

A natural structure is one WoT Event per process area or per category, and one Property for the server status. A gateway that exposes the Thing through OPC UA can then report the events of every process area through its own notifier Object.

Security Considerations

OPC A&E relies on the security of local COM, exactly as OPC DA does. The security considerations of [[WOT-OPCDA-BINDING]] apply unchanged, in particular:

  • COM checks the launch, activation, and access permissions of the server against the Windows account of the Consumer process, and a Consumer SHOULD run under a dedicated account with only the permissions it needs;
  • event notifications are calls from the server process into the Consumer, which therefore accepts incoming COM calls and SHOULD restrict them to the account of the server;
  • a Thing Description SHOULD describe an opcae endpoint with the nosec security scheme of [[WOT-THING-DESCRIPTION]], because the Consumer supplies no security information, while the operating system and the server still enforce their permissions;
  • a Consumer that exposes events or condition methods to other computers, for example through OPC UA, becomes responsible for authenticating and authorizing remote clients; and
  • servers can additionally implement the OPC Security interfaces [[OPC-SECURITY]].

Alarm acknowledgement and the disabling of conditions are safety-relevant operator actions. A disabled condition no longer produces alarms, and an acknowledged alarm may no longer be noticed by operators. A Consumer SHOULD only allow OPC UA users that are authorized as operators to call the condition methods. The OPC A&E server attributes every acknowledgement to the acknowledger ID that the Consumer passes, which becomes part of the alarm record, so the Consumer SHOULD pass the identity of the OPC UA user truthfully and SHOULD keep its own audit trail, for example with the OPC UA audit events for condition methods.

Event messages and attributes are text and values chosen by the server or by operators. A Consumer that displays them MUST treat them as untrusted input.

As in [[WOT-OPCDA-BINDING]], this binding does not yet define security scheme terms for passing OPC Security credentials.

Implementation Notes

  • OPC A&E uses COM and is therefore native to Microsoft Windows. A Consumer implementing this binding runs on the Windows computer of the server. Consumers on other computers or platforms access the server through a gateway that exposes it through another protocol, typically OPC UA as described in OPC UA Alarms and Conditions.
  • Out-of-process servers require the OPC proxy and stub libraries of the OPC Core Components, so that the OPC interfaces can be marshalled between the Consumer and the server process.
  • Events are often delivered in bursts, for example during a plant upset or a refresh. A Consumer SHOULD return from OnEvent quickly and process the events asynchronously, because the server waits for the callback to return.
  • The mappings of event types, event fields, and condition methods in this binding follow those of the OPC UA COM wrappers published by the OPC Foundation, so that OPC UA clients see the same alarms whether an OPC A&E server is accessed through such a wrapper or through a WoT gateway. Unlike those wrappers, this binding sets Retain from the condition state, so that OPC UA clients remove inactive and acknowledged alarms from their alarm lists.

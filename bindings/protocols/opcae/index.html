This Web of Things (WoT) protocol binding describes how a Thing Description exposes the alarms and events of an OPC Alarms and Events (OPC A&E) server [[OPC-AE]], one of the COM/DCOM-based OPC Classic specifications.

The binding defines:

  • the opcae URI scheme used to identify an OPC A&E server and its event sources;
  • event subscriptions for WoT Events, filtered by event type, category, severity, area, and source;
  • a JSON payload for simple, tracking, and condition-related event notifications;
  • reading the state of a condition;
  • acknowledging, enabling, and disabling conditions; and
  • mappings between WoT operations and the OPC A&E interfaces.

This protocol binding is not an OPC Foundation specification.

This document is a work in progress.

This initial version of the binding covers event subscriptions and condition management of OPC A&E 1.0 and 1.10 servers. It shares the URI layout and security considerations of the companion OPC DA Binding [[WOT-OPCDA-BINDING]] and OPC HDA Binding.

Introduction

OPC Alarms and Events is the OPC Classic specification for alarms and event notifications. An OPC A&E server is a COM server that runs on a Microsoft Windows computer and reports events detected by control systems, operator stations, or the server itself. Clients reach the server locally through COM or remotely through Distributed COM (DCOM) [[MS-DCOM]].

OPC A&E distinguishes three types of events:

  • simple events, such as a device failure or a batch completion;
  • tracking events, which report an action of an operator or another actor, such as a setpoint change; and
  • condition-related events, which report a change of a condition, such as HighAlarm or LevelAlarm, of a source, such as Plant1.Tank3.Level. A condition is active or inactive, acknowledged or unacknowledged, and enabled or disabled, and it has subconditions, such as HI and HIHI.

Every event has a category, a server-defined classification, and a severity from 1 to 1000. Sources are organized in a hierarchy of process areas. A client creates an event subscription, sets a filter on it, and receives the matching events through a callback.

A Thing Description [[WOT-THING-DESCRIPTION]] can describe OPC A&E event streams as WoT Events, the state of conditions as WoT Properties, and condition management as WoT Actions. The Thing Description supplies the server, the source, the filter, and the parameters that an implementation needs.

The following topics are outside the initial scope:

  • the OPC XML web service specifications;
  • event server configuration, such as defining conditions;
  • translating event attributes to OPC DA item IDs with TranslateToItemIDs; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the opcae scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the opcae URI scheme;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises; and
  4. converts event notifications and condition states into the JSON payloads specified.

The interoperable profile of this binding is the subset of its URI components, vocabulary terms, and behaviors that every conforming Consumer MUST support. A Thing Description that uses only the interoperable profile therefore works with every conforming Consumer, while anything outside it, such as a binding extension, is only understood by Consumers that implement that extension. Unless a section states otherwise, all URI components, vocabulary terms, and operation mappings defined normatively in this document belong to the interoperable profile.

OPC Classic Background

OPC Data Access (DA), OPC Historical Data Access (HDA), and OPC A&E are known together as OPC Classic. They share the following foundations, which this binding relies on:

  • A server is a COM class, identified by a class identifier (CLSID) and usually also by a programmatic identifier (ProgID) such as Vendor.OPCAEServer.1. A client creates the server object with CoCreateInstanceEx, on the local computer or, through DCOM, on a remote computer.
  • OPC A&E servers register themselves in the component category CATID_OPCAEServer10. The OPC Server Enumerator (OPCEnum), installed with the OPC Core Components, lets a remote client list the registered servers and translate a ProgID into a CLSID through IOPCServerList2 [[OPC-COMMON]].
  • All OPC Classic servers implement IOPCCommon and announce an orderly shutdown through the IOPCShutdown callback interface [[OPC-COMMON]].
  • Event notifications are delivered over COM connection points, so the server calls back into the client process. Over DCOM this requires both computers to accept calls from each other.

URI Scheme and Addressing

Server URI

An OPC A&E server is identified by an opcae URI:

opcae-URI = "opcae://" host "/" server-id "/"
server-id = progid / clsid

The components host, progid, and clsid, the resolution of a ProgID on a remote computer, and the prohibition of a port are defined exactly as for the opcda URI in [[WOT-OPCDA-BINDING]]. In particular, a Consumer MUST translate the ProgID of a remote server into a CLSID on the remote computer, the URI MUST NOT contain a port, and the base of a Thing Description MUST end with /. 

{
  "base": "opcae://alarms.example.com/Vendor.OPCAEServer.1/"
}

Source Reference

The resolved Form target identifies the server, or an event source or process area of the server:

opcae-source-URI = opcae-URI [ source-name ]

The source-name is the fully qualified name of a source, as reported in event notifications, for example Plant1.Tank3.Level. For the methods EnableConditionByArea and DisableConditionByArea, it is the fully qualified name of a process area instead. The name is a single path segment and is percent-encoded and decoded as specified for item IDs in [[WOT-OPCDA-BINDING]]: /, ?, #, %, [, ], \, and space MUST be percent-encoded, and a relative href whose name contains a colon MUST start with ./ or percent-encode the colon. An implementation MUST pass the percent-decoded name to the server exactly as written.

When the resolved target has no source-name, that is, when it equals the server URI, the Form addresses the server as a whole. Such a Form is typically written with the href "./".

OPC A&E Vocabulary

The examples use the prefix opcaev for the provisional namespace. The prefix intentionally differs from the opcae URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "opcaev": "https://www.w3.org/2026/wot/opcae"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Operation Mappings

Event Mappings

WoT operation OPC A&E mapping Requirements
subscribeevent
  1. Call IOPCEventServer::CreateEventSubscription with bActive set to FALSE, opcaev:bufferTime, and opcaev:maxSize.
  2. Call IOPCEventSubscriptionMgt::SetFilter with the filter given by the Form terms, see below.
  3. For every element of opcaev:returnedAttributes, call IOPCEventSubscriptionMgt::SelectReturnedAttributes.
  4. When opcaev:keepAlive is present, call IOPCEventSubscriptionMgt2::SetKeepAlive.
  5. Register an IOPCEventSink through the subscription's IConnectionPointContainer, and activate the subscription with IOPCEventSubscriptionMgt::SetState.
  6. When opcaev:refresh is true, call IOPCEventSubscriptionMgt::Refresh.
Every event of every IOPCEventSink::OnEvent callback for the subscription is a notification whose data is an event notification. 		The Form MUST NOT carry opcaev:method.
unsubscribeevent Unregister the IOPCEventSink and release the subscription object. When a refresh is in progress, the Consumer SHOULD first call IOPCEventSubscriptionMgt::CancelRefresh. None.

The filter passed to SetFilter is derived as follows:

  • the event type is the combination of OPC_SIMPLE_EVENT (1), OPC_TRACKING_EVENT (2), and OPC_CONDITION_EVENT (4) for the values of opcaev:eventTypes, or OPC_ALL_EVENTS (7) when the term is absent;
  • the categories, areas, and severities are those of opcaev:categories, opcaev:areas, opcaev:lowSeverity, and opcaev:highSeverity; and
  • the sources are those of opcaev:sources, or, when the resolved target contains a source-name, that single source. A Form whose target contains a source-name MUST NOT carry opcaev:sources.

A server reports the filters it supports with IOPCEventServer::QueryAvailableFilters. A Consumer MUST fail the subscription when the Form requests a filter that the server does not support, rather than silently deliver unfiltered events.

The server MAY revise the buffer time, the maximum size, and the keep-alive time, in which case it returns OPC_S_INVALIDBUFFERTIME, OPC_S_INVALIDMAXSIZE, or OPC_S_INVALIDKEEPALIVETIME. A Consumer MUST accept revised values and MAY warn about them. A Consumer MUST NOT deliver an empty keep-alive callback as a notification; it MAY use the absence of keep-alive callbacks to detect a broken connection.

Refresh

Event subscriptions only report changes. A Consumer that needs the current alarm situation, for example to fill an alarm list, sets opcaev:refresh to true. The server then sends a condition-related event for every condition that is active, or inactive and unacknowledged, and that matches the filter. These events are marked with "refresh": true in the notification, and they are delivered as notifications like any other event.

Condition Mappings

The term opcaev:method selects the condition method that a Form invokes. The following values are defined:

Value WoT operation OPC A&E mapping
GetConditionState readproperty Call IOPCEventServer::GetConditionState with the source from the resolved target, opcaev:condition, and opcaev:attributeIds, and return the condition state.
AckCondition invokeaction Call IOPCEventServer::AckCondition for a single condition, with the parameters described in Acknowledgement.
EnableConditionBySource, DisableConditionBySource invokeaction Call the method of the same name of IOPCEventServer with the source from the resolved target, or with the members of the sources array of the action input when the target has no source-name.
EnableConditionByArea, DisableConditionByArea invokeaction Call the method of the same name of IOPCEventServer with the area from the resolved target, or with the members of the areas array of the action input when the target has no source-name.

A Form MUST only contain the WoT operation listed for its method. A Form containing invokeaction MUST carry opcaev:method. Enabling and disabling conditions has no output.

The OPC A&E condition state has no change notification of its own; changes are reported as condition-related events. No default mapping is therefore defined for observeproperty and unobserveproperty, and a Thing Description that needs to follow a condition SHOULD use a WoT Event whose Form filters for the source of the condition.

Acknowledgement

An AckCondition action acknowledges one condition. Its input is a JSON object with the following members, named like the members of an event notification so that a notification can be passed back unchanged:

Member Description Assignment
source Source of the condition. required when the resolved target has no source-name, otherwise ignored
condition Name of the condition. required unless the Form carries opcaev:condition
activeTime Active time of the condition, as received in the event notification. required
cookie Cookie of the condition, as received in the event notification. required
comment Comment stored with the acknowledgement. optional
acknowledgerId Identity of the operator or application that acknowledges the condition. optional, default opcaev:acknowledgerId

Members of the input that are not listed are ignored. The Consumer MUST pass a non-empty acknowledger ID; when neither the input nor the Form supplies one, the Consumer SHOULD use the name of the user on whose behalf it acts. The server rejects an acknowledgement whose active time and cookie do not match the current activation of the condition with OPC_E_INVALIDTIME, which the Consumer MUST report as an error. A condition that is already acknowledged returns OPC_S_ALREADYACKED, which the Consumer MUST treat as success. The action has no output.

Server Status

A Form whose resolved target equals the server URI and that contains the readproperty operation addresses the server status. Such a Form MUST NOT carry opcaev:method or opcaev:condition. readproperty calls IOPCEventServer::GetStatus and returns an object with the members state, startTime, currentTime, lastUpdateTime, version, and vendorInfo, converted from the OPCEVENTSERVERSTATUS fields as defined for the OPC DA server status in [[WOT-OPCDA-BINDING]]. The values of state are running, failed, noConfig, suspended, test, and commFault, for OPCAE_STATUS_RUNNING to OPCAE_STATUS_COMM_FAULT.

Server Shutdown

A Consumer SHOULD register an IOPCShutdown callback with the server [[OPC-COMMON]]. When the server calls ShutdownRequest, the Consumer MUST release all references to the server, MUST end all active subscriptions with an error that includes the reason supplied by the server, and MAY reconnect later. After reconnecting, the Consumer SHOULD request a refresh, because events that occurred in the meantime are lost.

Error Handling

OPC A&E reports errors as HRESULT codes. A Consumer MUST report a failed operation to the application when the call or a per-condition result fails. The following codes are particularly relevant:

Code Meaning Consumer behavior
E_INVALIDARG A parameter is invalid, for example an unknown category or an inverted severity range in the filter, or an unknown area or source. Fail the operation.
OPC_E_INVALIDTIME The active time and cookie of an acknowledgement do not match the condition. Fail the operation.
OPC_S_ALREADYACKED The condition is already acknowledged. Succeed.
OPC_E_NOINFO The server has no state information for the source and condition. Fail the operation.
OPC_E_BUSY A refresh is already in progress for the subscription. Fail the subscription, or retry the refresh later.
OPC_S_INVALIDBUFFERTIME, OPC_S_INVALIDMAXSIZE, OPC_S_INVALIDKEEPALIVETIME The server revised a subscription parameter. Succeed, and MAY warn.

Payload Mapping

Event Notifications

Every event delivered in an ONEVENTSTRUCT is represented at the WoT Consumer boundary as a JSON object with the following members. Members marked as condition-related are only present for condition-related events, and actorId is only present for tracking events.

Member ONEVENTSTRUCT field Value
source szSource string
time ftTime [[RFC3339]] date-time in UTC
message szMessage string
eventType dwEventType One of simple, tracking, and condition
category dwEventCategory integer
severity dwSeverity integer, from 1 to 1000
attributes pEventAttributes Object whose member names are the decimal attribute identifiers selected with opcaev:returnedAttributes and whose values are converted as described for OPC DA item values in [[WOT-OPCDA-BINDING]]; present when attributes were selected for the category
refresh bRefresh parameter of OnEvent boolean; present and true only for events sent because of a refresh
actorId szActorID string; tracking events only
condition szConditionName string; condition-related
subCondition szSubconditionName string; condition-related
changeMask wChangeMask Array of the strings activeState, ackState, enableState, quality, severity, subCondition, message, and attribute, for the bits OPC_CHANGE_ACTIVE_STATE (0x01) to OPC_CHANGE_ATTRIBUTE (0x80) that are set; condition-related
state wNewState Object with the boolean members enabled, active, and acknowledged, for the bits OPC_CONDITION_ENABLED (1), OPC_CONDITION_ACTIVE (2), and OPC_CONDITION_ACKED (4); condition-related
quality wQuality integer, from 0 to 65535, as the OPC DA quality; condition-related
ackRequired bAckRequired boolean; condition-related
activeTime ftActiveTime [[RFC3339]] date-time in UTC, with the full precision of the server time; condition-related
cookie dwCookie integer, from 0 to 4294967295; condition-related

A Consumer MUST preserve the full 100-nanosecond precision of ftActiveTime in activeTime, using up to seven fractional digits, because AckCondition requires the exact active time. 

{
  "source": "Plant1.Tank3.Level",
  "time": "2026-11-17T07:42:10.1250000Z",
  "message": "Tank 3 level high",
  "eventType": "condition",
  "category": 3,
  "severity": 700,
  "condition": "LevelAlarm",
  "subCondition": "HI",
  "changeMask": ["activeState", "severity", "subCondition", "message"],
  "state": { "enabled": true, "active": true, "acknowledged": false },
  "quality": 192,
  "ackRequired": true,
  "activeTime": "2026-11-17T07:42:10.1250000Z",
  "cookie": 18734
}

Member OPCCONDITIONSTATE field Value

activeSubCondition szActiveSubCondition string
definition szASCDefinition string, the definition of the active subcondition
severity dwASCSeverity integer, the severity of the active subcondition
description szASCDescription string, the description of the active subcondition
quality wQuality integer
lastAckTime ftLastAckTime [[RFC3339]] date-time
subConditionLastActive ftSubCondLastActive [[RFC3339]] date-time
conditionLastActive ftCondLastActive [[RFC3339]] date-time

Generating Thing Descriptions

OPC A&E servers describe their event space. A tool that generates a Thing Description can use the following methods of IOPCEventServer:

  • QueryEventCategories lists the categories of each event type, which give values for opcaev:categories;
  • QueryEventAttributes lists the attributes of each category with their data types, which give opcaev:returnedAttributes and the Data Schema of the attributes member;
  • QueryConditionNames and QuerySubConditionNames list the conditions and subconditions, which give opcaev:condition and an enum for subCondition;
  • CreateAreaBrowser walks the process area hierarchy, which gives values for opcaev:areas, and QuerySourceConditions lists the conditions of each source found; and
  • QueryAvailableFilters tells which filter terms the server supports.

A natural structure is one WoT Event per process area or per category, one Property per condition whose state is of interest, and one AckCondition Action per Thing.

Security Considerations

OPC A&E relies on the security of COM and DCOM [[MS-DCOM]], exactly as OPC DA does. The security considerations of [[WOT-OPCDA-BINDING]] apply unchanged, in particular:

  • a Consumer SHOULD use the authentication level RPC_C_AUTHN_LEVEL_PKT_PRIVACY and MUST use at least RPC_C_AUTHN_LEVEL_PKT_INTEGRITY for remote servers [[KB5004442]];
  • event notifications are calls from the server into the Consumer, which therefore accepts incoming DCOM calls and SHOULD restrict them to the account of the server;
  • a Thing Description SHOULD describe an opcae endpoint with the auto security scheme of [[WOT-THING-DESCRIPTION]], and nosec MUST NOT be used for a remote server; and
  • servers can additionally implement the OPC Security interfaces [[OPC-SECURITY]].

Alarm acknowledgement and the disabling of conditions are safety-relevant operator actions. A disabled condition no longer produces alarms, and an acknowledged alarm may no longer be noticed by operators. A Thing Description SHOULD only expose these Actions where the application requires it, and a Consumer SHOULD require an explicit user decision before invoking them and SHOULD record the acknowledger ID truthfully, because it becomes part of the alarm record.

Event messages and attributes are text and values chosen by the server or by operators. A Consumer that displays them MUST treat them as untrusted input.

As in [[WOT-OPCDA-BINDING]], this binding does not yet define security scheme terms for selecting the DCOM authentication level and impersonation level, or for passing explicit Windows or OPC Security credentials.

Implementation Notes

  • OPC A&E uses COM and is therefore native to Microsoft Windows. Consumers on other platforms need a DCOM implementation of their own, or a gateway that exposes the server through another protocol, such as an OPC UA wrapper of an OPC A&E server.
  • Remote access requires the OPC proxy and stub libraries of the OPC Core Components on both computers, and the OPC Server Enumerator on the server computer for ProgID resolution.
  • Events are often delivered in bursts, for example during a plant upset or a refresh. A Consumer SHOULD return from OnEvent quickly and process the events asynchronously, because the server waits for the callback to return.
  • The OPC A&E condition model was carried over into OPC UA Part 9, Alarms and Conditions, so the condition names, states, and acknowledgement semantics of this binding remain recognizable when a server is later accessed through OPC UA.

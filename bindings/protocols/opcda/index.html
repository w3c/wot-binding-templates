This Web of Things (WoT) protocol binding describes how a Thing Description exposes the items of an OPC Data Access (OPC DA) server [[OPC-DA]] [[OPC-DA-2]], one of the COM-based OPC Classic specifications.

The binding is limited to local COM: the Consumer and the OPC DA server run on the same computer. Remote access through Distributed COM (DCOM) is not supported, see COM Only.

The binding defines:

  • the opcda URI scheme used to identify a local OPC DA server and the items in its address space;
  • item addressing in WoT Forms, including the optional access path;
  • the requested data type of an item, based on the COM VARTYPE of the item value;
  • cache and device reads, controlled by a maximum age;
  • native subscriptions for observed properties, controlled by the update rate and percent deadband of an OPC group;
  • the quality and timestamp of every value, delivered as metadata that corresponds to an OPC UA status code and source timestamp;
  • access to item properties and to the server status; and
  • mappings between WoT property operations and the OPC DA interfaces.

This protocol binding is not an OPC Foundation specification.

This document is a work in progress.

This initial version of the binding covers reading, writing, and subscribing to the items of OPC DA 2.0 and 3.0 servers through local COM. Servers that implement only OPC DA 1.0a are covered for reads and writes. DCOM is not covered. Historical data and alarms are covered by the companion OPC HDA Binding and OPC A&E Binding, which share the URI layout and security considerations of this document.

Introduction

OPC Data Access is the original OPC specification, published by the OPC Foundation and widely deployed in process and factory automation. An OPC DA server is a COM server that runs on a Microsoft Windows computer and gives clients access to current process values, called items, which it obtains from controllers, field devices, or other data sources. Clients on the same computer reach the server through COM. The OPC DA specification also allows remote clients through Distributed COM (DCOM) [[MS-DCOM]], which this binding does not support.

Each item is identified by an item ID, a server-specific string such as Channel1.Device1.Temperature. A client reads or writes an item synchronously or asynchronously, and subscribes to changes by adding the item to an OPC group that the server scans at a requested update rate. Every item value is returned together with a quality and a timestamp.

A Thing Description [[WOT-THING-DESCRIPTION]] can describe OPC DA items as WoT Properties. The Thing Description supplies the server, the item ID, the supported WoT operations, the requested data type, and the subscription parameters that an implementation needs.

The following topics are outside the initial scope:

  • remote access through DCOM, see COM Only;
  • the OPC XML-DA web service specification;
  • OPC Complex Data and OPC Data eXchange (DX);
  • batched reads and writes across several Forms as a normative behavior;
  • server configuration, such as creating or deleting items in the server; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the opcda scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the opcda URI scheme and rejects URIs that do not address the local computer;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises;
  4. converts between the OPC DA VARIANT value and the WoT Data Schema as specified; and
  5. evaluates the OPC quality of every value it delivers.

The interoperable profile of this binding is the subset of its URI components, vocabulary terms, and behaviors that every conforming Consumer MUST support. A Thing Description that uses only the interoperable profile therefore works with every conforming Consumer, while anything outside it, such as a binding extension, is only understood by Consumers that implement that extension. Unless a section states otherwise, all URI components, vocabulary terms, and operation mappings defined normatively in this document belong to the interoperable profile.

OPC Classic Background

OPC DA, OPC Historical Data Access (HDA), and OPC Alarms and Events (A&E) are known together as OPC Classic. They share the following foundations, which this binding and its companion bindings rely on:

  • A server is a COM class, identified by a class identifier (CLSID) and usually also by a programmatic identifier (ProgID) such as Vendor.OPCServer.1. A client creates the server object with CoCreateInstance. Most OPC servers are out-of-process servers, that is, separate executables that COM starts on demand.
  • Servers register themselves in component categories, for example CATID_OPCDAServer20 and CATID_OPCDAServer30, which lets a client list the OPC DA servers installed on the computer.
  • All OPC Classic servers implement IOPCCommon and announce an orderly shutdown through the IOPCShutdown callback interface [[OPC-COMMON]].
  • Callbacks, such as data change notifications, are delivered over COM connection points, so the server calls back into the client process.

COM Only

This binding, like its companion OPC HDA and OPC A&E bindings, only covers access to an OPC Classic server through local COM. The Consumer MUST run on the same computer as the server. Access to a server on another computer through DCOM [[MS-DCOM]] is outside the scope of this binding, and a Consumer MUST NOT use DCOM to realize an opcda Form.

This is a deliberate limitation. Although the OPC Classic specifications allow DCOM, it is generally not used in industry today: it requires complex and fragile firewall and permission configuration, its dynamic ports are hard to secure, and the DCOM hardening changes of recent Windows versions have broken many existing installations. Remote access to OPC Classic servers is instead commonly provided by OPC UA wrappers or tunnelling products that run next to the server.

URI Scheme and Addressing

Server URI

An OPC DA server is identified by an opcda URI:

opcda-URI = "opcda://localhost/" server-id "/"
server-id = progid / clsid

Where:

  • the host is always localhost, because the server runs on the same computer as the Consumer, see COM Only. A Consumer MUST reject an opcda URI with any other host, including an IP address of the local computer;
  • progid is the ProgID of the server, for example Vendor.OPCServer.1, or its version-independent ProgID; and
  • clsid is the CLSID of the server in its 36-character registry form without braces, for example F8582CF2-88FB-11D0-B850-00C0F0104305. A Consumer MUST also accept the braced form, in which the braces are percent-encoded as %7B and %7D.

A ProgID consists of letters, digits, and periods only, and starts with a letter, so it cannot be mistaken for a CLSID. When server-id is a ProgID, the Consumer translates it into a CLSID with CLSIDFromProgID. A Thing Description MAY use the CLSID to identify a specific server version unambiguously.

The URI MUST NOT contain a port, user information, query, or fragment, because COM uses none of them.

A Thing Description SHOULD place the server URI in base and use relative item references in individual Forms. The base MUST end with /; otherwise reference resolution [[RFC3986]] replaces the server identifier with the item ID. 

{
  "base": "opcda://localhost/Vendor.OPCServer.1/"
}

The scheme names opcda, opchda, and opcae and the host/ProgID path follow the URL convention of the OPC Foundation's OPC .NET API. That convention also allows a remote host and a CLSID path segment after the ProgID. This binding allows neither: the host is always localhost, and the path segment after the server identifier carries the item ID.

Item Reference

The resolved Form target identifies an item of the server:

opcda-item-URI = opcda-URI [ item-id ]

The item-id is the fully qualified item ID as defined by the server, for example Channel1.Device1.Temperature or Random.Int4. Its syntax is server-specific: some servers use . as a hierarchy separator, others use /, \, or :, and item IDs can contain spaces. An implementation MUST pass the percent-decoded item ID to the server exactly as written, because item IDs are opaque to the client and their case sensitivity is defined by the server.

When the resolved target has no item-id, that is, when it equals the server URI, the Form addresses the server object itself, see Server Status. 

{
  "href": "Channel1.Device1.Temperature",
  "op": ["readproperty"]
}

When the Thing Description contains "base": "opcda://localhost/Vendor.OPCServer.1/", the resolved target is opcda://localhost/Vendor.OPCServer.1/Channel1.Device1.Temperature.

Some servers additionally use an access path, a hint that selects the communication path to the data source. Because it is not part of the item identity in most servers, it is carried by the Form term opcdav:accessPath rather than by the URI.

Reserved Characters

The item ID is a single path segment. Authors MUST percent-encode any character of an item ID that is not allowed in a path segment [[RFC3986]], and in particular MUST percent-encode / as %2F, ? as %3F, # as %23, % as %25, [ as %5B, ] as %5D, \ as %5C, and a space as %20.

A colon in the first segment of a relative reference is not allowed by [[RFC3986]]: a relative href such as PLC1:DB10.Speed would be parsed as an absolute URI with the scheme PLC1. A relative href whose item ID contains a colon MUST therefore either start with ./, as in ./PLC1:DB10.Speed, or percent-encode the colon as %3A. Authors SHOULD use the ./ form.

The character . needs no encoding. Reference resolution removes a leading ./, and an implementation MUST percent-decode the item ID of the resolved URI before passing it to the server. 

Channel1.Device1.Temperature
./PLC1:DB10.Speed
Area%201%2FBoiler%2FPressure

OPC DA Vocabulary

The examples use the prefix opcdav for the provisional namespace. The prefix intentionally differs from the opcda URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "opcdav": "https://www.w3.org/2026/wot/opcda"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Form Terms

opcdav:type Data type in which the Consumer requests the item value from the server, see Data Types. optional, default is the canonical data type of the item string (one of the values in Data Types)
opcdav:array Indicates that the item value is a one-dimensional array whose elements have the type given by opcdav:type. optional, default false boolean

opcdav:deadband Percent deadband applied to an analog item for observeproperty, see Subscriptions. optional, default 0 float, from 0 to 100
opcdav:propertyId Identifier of an item property to read instead of the item value, see Item Properties. optional unsignedInt
opcdav:timeout Maximum time to wait for the server response, in milliseconds. optional unsignedInt

Data Types

OPC DA transfers item values as COM VARIANT values. Every item has a canonical data type, the VARTYPE in which the server natively holds the value. A client can request a different data type, which the server then converts to and from. The binding identifies the requested data type with the following terms. The second column gives the VARTYPE and its numeric value, and the third column gives the recommended WoT Data Schema.

Value VARTYPE WoT Data Schema recommendation
opcdav:VT_BOOL Boolean, VT_BOOL (11) boolean
opcdav:VT_I1 Signed 8-bit integer, VT_I1 (16) integer, minimum -128, maximum 127
opcdav:VT_UI1 Unsigned 8-bit integer, VT_UI1 (17) integer, minimum 0, maximum 255
opcdav:VT_I2 Signed 16-bit integer, VT_I2 (2) integer, minimum -32768, maximum 32767
opcdav:VT_UI2 Unsigned 16-bit integer, VT_UI2 (18) integer, minimum 0, maximum 65535
opcdav:VT_I4 Signed 32-bit integer, VT_I4 (3) integer, minimum -2147483648, maximum 2147483647
opcdav:VT_UI4 Unsigned 32-bit integer, VT_UI4 (19) integer, minimum 0, maximum 4294967295
opcdav:VT_I8 Signed 64-bit integer, VT_I8 (20) integer
opcdav:VT_UI8 Unsigned 64-bit integer, VT_UI8 (21) integer, minimum 0
opcdav:VT_R4 IEEE 754 single-precision floating point, VT_R4 (4) number
opcdav:VT_R8 IEEE 754 double-precision floating point, VT_R8 (5) number
opcdav:VT_CY Currency, a 64-bit integer scaled by 10,000, VT_CY (6) number
opcdav:VT_DATE OLE Automation date, VT_DATE (7) string, format date-time
opcdav:VT_BSTR Unicode string, VT_BSTR (8) string

When opcdav:type is absent, the Consumer requests the canonical data type (VT_EMPTY) and converts the returned value according to its actual VARTYPE. When opcdav:type is present, the Consumer MUST request that type in the vtRequestedDataType member of the item definition, or as the VARTYPE of the value it writes. A server that cannot convert the value to the requested type fails the request with OPC_E_BADTYPE, which the Consumer MUST report as an error.

When opcdav:array is true, the requested type is the combination of VT_ARRAY with the element type given by opcdav:type, the value is a one-dimensional SAFEARRAY, and it is represented as a JSON array whose elements follow the table above. A Form that sets opcdav:array MUST also carry opcdav:type.

The following conversion rules apply:

  • A VT_BOOL value is VARIANT_TRUE (-1) or VARIANT_FALSE (0). The Consumer MUST map VARIANT_TRUE to true and MUST write VARIANT_TRUE, not 1, for true.
  • A VT_DATE value, which counts days since 30 December 1899, carries no time zone. The Consumer MUST interpret it in the time zone given by the item's time zone property (108) when the server provides that property, and in UTC otherwise, and MUST represent it as a [[RFC3339]] date-time with the corresponding offset.
  • A VT_CY value MUST be divided by 10,000 when reading and multiplied by 10,000 when writing.
  • JSON numbers cannot represent every 64-bit integer exactly. A Consumer that exposes VT_I8 or VT_UI8 values beyond 253 SHOULD warn about the loss of precision.

Implementations MUST reject an unsupported type rather than silently decode it as another type.

Cache and Device Reads

An OPC DA server keeps a cache of the values of the items it scans and can also read a value directly from the underlying device. Device reads are accurate but put load on the device and the communication link. The term opcdav:maxAge states how old a value returned by readproperty may be:

  • The value 0, the default, requests a device read.
  • A positive value allows the server to return its cached value when that value is not older than opcdav:maxAge milliseconds, and requires a device read otherwise.
  • The value 4294967295 (0xFFFFFFFF) requests the cached value regardless of its age.

These are the semantics of the dwMaxAge parameter of OPC DA 3.0 [[OPC-DA]], so a Consumer connected to an OPC DA 3.0 server passes the value unchanged. How a Consumer realizes them on older servers is described in Default Mappings.

Subscriptions

OPC DA servers notify clients of value changes. A client adds items to an OPC group, and the server scans the active items of an active group at the group's update rate and sends a data change notification for every item whose value or quality has changed. The Form terms opcdav:updateRate and opcdav:deadband describe the group used for observeproperty.

opcdav:updateRate is the requested update rate of the group in milliseconds. The value 0 requests the fastest practical rate of the server. When the term is absent, the Consumer chooses the rate. The server MAY revise the requested rate, in which case it returns OPC_S_UNSUPPORTEDRATE and the revised rate. A Consumer MUST accept a revised rate and MAY warn about it.

opcdav:deadband is a percent deadband. It applies only to items whose engineering unit type is analog (OPC_ANALOG); for those items the server suppresses a notification when the value has changed by less than the given percentage of the engineering unit range, that is, of the difference between the item's high and low engineering unit limits. For other items the server ignores the deadband.

A Consumer MAY place the items of several Forms with the same opcdav:updateRate into one group. When those Forms have different opcdav:deadband values, the Consumer MUST either use separate groups or, on an OPC DA 3.0 server, set the deadband of each item with IOPCItemDeadbandMgt::SetItemDeadband.

Item Properties

Besides its value, every OPC DA item has item properties that describe it, identified by numeric property identifiers. A Form that carries opcdav:propertyId reads the identified property of the item instead of the item value. The following property identifiers are defined by [[OPC-DA]]; identifiers from 5000 upward are vendor-specific.

Identifier Property Typical use in a Thing Description
1 Item canonical data type opcdav:type and the Data Schema type
2, 3, 4 Item value, quality, and timestamp none; use the item value instead
5 Item access rights (OPC_READABLE = 1, OPC_WRITEABLE = 2) readOnly and writeOnly
6 Server scan rate opcdav:updateRate
7, 8 Engineering unit type and engineering unit information applicability of opcdav:deadband; labels of enumerated items
100 Engineering units unit
101 Item description description
102, 103 High and low engineering unit limits range used for the percent deadband
104, 105 High and low instrument range range of the instrument
108 Item time zone interpretation of VT_DATE values

A Form that carries opcdav:propertyId MUST only contain the readproperty operation, and MUST NOT carry opcdav:updateRate or opcdav:deadband. The value of the property is converted as described in Data Types, using opcdav:type when present.

Operation Mappings

Default Mappings

A Consumer determines the OPC DA version of a server by querying the server object for its interfaces: IOPCItemIO indicates OPC DA 3.0, and a connection point for IOPCDataCallback on the group object indicates OPC DA 2.0 or later. The mappings for Forms that address an item are:

WoT operation OPC DA 3.0 OPC DA 2.0 and 1.0a Requirements
readproperty Call IOPCItemIO::Read with the item ID and opcdav:maxAge as dwMaxAge, and convert the returned value, quality, and timestamp. Add the item to a group with IOPCItemMgt::AddItems and call IOPCSyncIO::Read with OPC_DS_DEVICE. The Consumer MAY use OPC_DS_CACHE instead when opcdav:maxAge is positive and the item is active in an active group whose revised update rate does not exceed opcdav:maxAge. The item access rights MUST include OPC_READABLE.
writeproperty Convert the supplied value and call IOPCItemIO::WriteVQT without specifying a quality or timestamp. Add the item to a group and call IOPCSyncIO::Write with the converted value. The item access rights MUST include OPC_WRITEABLE, and the property MUST NOT be declared readOnly: true.
observeproperty Create a group with IOPCServer::AddGroup, passing opcdav:updateRate as the requested update rate and opcdav:deadband as the percent deadband, add the item as an active item, and register an IOPCDataCallback through the group's IConnectionPointContainer. Every OnDataChange callback for the item is a notification. The first notification after the item has been added carries its current value. observable SHOULD be true. The server MUST implement OPC DA 2.0 or later.
unobserveproperty Remove the item from the group with IOPCItemMgt::RemoveItems. When the group has no remaining items, unadvise the callback and remove the group with IOPCServer::RemoveGroup. None.

In every item definition the Consumer MUST pass the item ID from the resolved href, the access path from opcdav:accessPath, and the requested data type from opcdav:type and opcdav:array. A Consumer MAY reuse groups and items across operations and Forms, and MAY combine the items of several Forms of the same server into a single call, to reduce the load on the server.

Servers that implement only OPC DA 1.0a provide no IOPCDataCallback connection point. A Consumer MAY realize observeproperty for them with the OPC DA 1.0a IDataObject advise mechanism or by polling, but this is not part of the [=interoperable profile=].

Item Property Mappings

A readproperty operation on a Form that carries opcdav:propertyId calls IOPCBrowse::GetProperties on an OPC DA 3.0 server, or IOPCItemProperties::GetItemProperties on an OPC DA 2.0 server, for the item ID and the given property identifier, and converts the returned value. A server that does not know the property fails the request with OPC_E_INVALID_PID, which the Consumer MUST report as an error.

Server Status

A Form whose resolved target equals the server URI addresses the server object. Such a Form MUST only contain the readproperty and observeproperty operations. readproperty calls IOPCServer::GetStatus and returns an object with the following members:

Member OPCSERVERSTATUS field Value
state dwServerState One of running, failed, noConfig, suspended, test, and commFault, for OPC_STATUS_RUNNING to OPC_STATUS_COMM_FAULT
startTime ftStartTime [[RFC3339]] date-time
currentTime ftCurrentTime [[RFC3339]] date-time
lastUpdateTime ftLastUpdateTime [[RFC3339]] date-time
groupCount dwGroupCount integer
bandWidth dwBandWidth integer
version wMajorVersion, wMinorVersion, wBuildNumber string of the form major.minor.build
vendorInfo szVendorInfo string

The OPC DA server status has no change notification, so observeproperty on the server object is realized by calling IOPCServer::GetStatus repeatedly, at the interval given by opcdav:updateRate, and notifying the Consumer when the result changes. An implementation MAY enforce a minimum interval.

Server Shutdown

A Consumer SHOULD register an IOPCShutdown callback with the server [[OPC-COMMON]]. When the server calls ShutdownRequest, the Consumer MUST release all references to the server, MUST end all active observations with an error that includes the reason supplied by the server, and MAY reconnect later.

Action and Event Mappings

No default mapping is defined for:

  • invokeaction;
  • subscribeevent;
  • unsubscribeevent; or
  • WoT Event affordances.

A Thing Description conforming to the profile MUST NOT advertise those operations on an opcda Form unless it also declares and documents an additional binding extension. Alarms and events of OPC Classic servers are described with the OPC A&E Binding.

Error Handling

OPC DA reports errors per item as HRESULT codes. A Consumer MUST report a failed operation to the application when the call or the per-item result fails. The following codes are particularly relevant:

Code Meaning Consumer behavior
OPC_E_UNKNOWNITEMID, OPC_E_INVALIDITEMID The item ID is not known to the server or is syntactically invalid. Fail the operation.
OPC_E_UNKNOWNPATH The access path is not known to the server. Fail the operation.
OPC_E_BADRIGHTS The item is not readable or not writable. Fail the operation.
OPC_E_BADTYPE The server cannot convert between the requested and the canonical data type. Fail the operation.
OPC_E_RANGE The written value is out of range. Fail the operation.
OPC_S_CLAMP The written value was accepted but clamped. Succeed, and MAY warn.
OPC_S_UNSUPPORTEDRATE The server revised the requested update rate. Succeed, and MAY warn.
OPC_E_DEADBANDNOTSUPPORTED The item does not support a deadband. Fail the operation.
OPC_E_INVALID_PID The item property identifier is not valid for the item. Fail the operation.

Payload Mapping

Values

An item value is represented at the WoT Consumer boundary as the JSON value compatible with the Property's WoT Data Schema. The binding implementation is responsible for converting between that value and the VARIANT exchanged with the server, as described in Data Types.

A Consumer MUST use both the WoT Data Schema and opcdav:type. The WoT Data Schema describes the application-facing value, while the Form term identifies the representation requested from the server.

Quality and Timestamp

OPC DA returns every value together with a 16-bit quality and a UTC timestamp [[OPC-DA]]. They are metadata of the value rather than part of the payload: the WoT Data Schema does not describe them, and a Consumer that makes them available to the application does so alongside the value, through implementation-specific means.

This matches OPC UA, where the value of a Variable is accompanied by a status code and a source timestamp. A Consumer that exposes the Property as an OPC UA Variable, for example in a gateway, SHOULD map them as follows:

OPC DA OPC UA
quality OPC_QUALITY_GOOD status code with severity Good
quality OPC_QUALITY_UNCERTAIN status code with severity Uncertain
quality OPC_QUALITY_BAD status code with severity Bad
limit bits low, high, and constant limit bits Low, High, and Constant of the status code
timestamp SourceTimestamp

The two most significant bits of the quality select OPC_QUALITY_GOOD, OPC_QUALITY_UNCERTAIN, or OPC_QUALITY_BAD. The following rules apply:

  • A value with good quality is delivered as is.
  • A value with uncertain quality is delivered, and the Consumer SHOULD make the quality available to the application.
  • A value with bad quality MUST NOT be delivered as a valid value. The Consumer either delivers it together with its quality, for example as an OPC UA value with a Bad status code, or fails the readproperty operation and suppresses or reports as an error the notification of an observeproperty operation.

When writing, only the value is supplied. The server sets the quality and timestamp of the written value.

Generating Thing Descriptions

OPC DA servers are browsable. A tool that generates a Thing Description can walk the server address space with IOPCBrowse::Browse on an OPC DA 3.0 server, or with IOPCBrowseServerAddressSpace on an OPC DA 2.0 server, and create one Property for every leaf item, using the fully qualified item ID as the href. It can then read the item properties to fill in the Property:

  • the canonical data type (1) gives opcdav:type and the Data Schema type;
  • the access rights (5) give readOnly when the item is not writable and writeOnly when it is not readable;
  • the engineering units (100) and the item description (101) give unit and description;
  • for an enumerated item (engineering unit type 2), the engineering unit information (8) is an array of labels indexed by the item value, which can be recorded in the description; and
  • the server scan rate (6) is a reasonable choice for opcdav:updateRate.

The high and low engineering unit limits (102, 103) define the nominal range used for the percent deadband, and values outside that range are allowed. They should therefore not be mapped to minimum and maximum unless the server enforces them.

Security Considerations

Because this binding only uses local COM, no OPC DA traffic leaves the computer, and the binding exposes no network endpoint of its own. A Thing Description MUST accurately describe the security applied to the interaction endpoint.

  • COM checks the launch, activation, and access permissions configured for the server against the Windows account under which the Consumer process runs. The Consumer supplies no credentials of its own; its authorization is determined entirely by that account.
  • A Consumer SHOULD run under a dedicated account with only the COM permissions it needs, rather than under an administrative account, and the server SHOULD grant access only to the accounts that need it.
  • Data change notifications and shutdown requests are calls from the server process into the Consumer process. A Consumer SHOULD restrict incoming COM calls to the account of the server.
  • Some servers additionally implement the OPC Security interfaces [[OPC-SECURITY]], which allow a client to log on as a specific user with IOPCSecurityPrivate::Logon.

Because the Consumer does not supply any security information to access the server, a Thing Description SHOULD describe an opcda endpoint with the nosec security scheme of [[WOT-THING-DESCRIPTION]], as the examples in this document do. This does not mean that access is unrestricted: the operating system and the server still enforce the permissions described above.

A Consumer that exposes OPC DA items to other computers, for example as a WoT gateway, makes them reachable through a network protocol. Such a Consumer becomes responsible for authenticating and authorizing remote clients, because the server sees every request as coming from the Consumer's account.

A binding implementation MUST NOT infer that a successful connection authorizes every operation. The server enforces item access rights, and it can reject a write with OPC_E_BADRIGHTS for the current user.

This binding does not yet define security scheme terms for passing OPC Security credentials. These are expected to be added once implementation experience is collected.

Implementation Notes

  • OPC DA uses COM and is therefore native to Microsoft Windows. A Consumer implementing this binding runs on the Windows computer of the server. Consumers on other computers or platforms access the server through a gateway that exposes it through another protocol, such as an OPC UA wrapper of an OPC DA server.
  • Out-of-process servers require the OPC proxy and stub libraries of the OPC Core Components, so that the OPC interfaces can be marshalled between the Consumer and the server process.
  • The URI scheme follows the URL convention of the OPC Foundation's OPC .NET API, which uses opcda, opchda, and opcae to select the OPC Classic specification and the URL path to select the server.
  • OPC UA wrappers of OPC DA servers typically expose each item as an OPC UA Variable. Because this binding represents an item as a plain value with its quality and timestamp as metadata, a Thing Description maps directly to such Variables, and the item IDs and data types remain recognizable when a server is later accessed through a wrapper.

This Web of Things (WoT) protocol binding describes how a Thing Description exposes the history of the items of an OPC Historical Data Access (OPC HDA) server [[OPC-HDA]], one of the COM/DCOM-based OPC Classic specifications.

The binding defines:

  • the opchda URI scheme used to identify an OPC HDA server and the items it historizes;
  • absolute and relative time ranges in WoT Forms, using the relative time syntax of OPC HDA;
  • raw, processed, at-time, and modified history reads, and the aggregates used by processed reads;
  • history updates, deletions, and annotations;
  • subscriptions to newly historized raw or processed values;
  • a time series payload that carries the value, quality, and timestamp of every historical value; and
  • mappings between WoT operations and the OPC HDA interfaces.

This protocol binding is not an OPC Foundation specification.

This document is a work in progress.

This initial version of the binding covers the synchronous read, update, and annotation interfaces and the asynchronous advise operations of OPC HDA 1.20 servers. It shares the URI layout and security considerations of the companion OPC DA Binding [[WOT-OPCDA-BINDING]] and OPC A&E Binding.

Introduction

OPC Historical Data Access is the OPC Classic specification for process historians. An OPC HDA server is a COM server that runs on a Microsoft Windows computer and gives clients access to the archived values of items, which it typically collects from OPC DA servers or directly from control systems. Clients reach the server locally through COM or remotely through Distributed COM (DCOM) [[MS-DCOM]].

Each item is identified by an item ID, a server-specific string such as Plant1.Unit3.FlowRate. A client reads the raw values stored for an item in a time range, or lets the server compute processed values, such as averages or minima, over consecutive resample intervals with an aggregate. Every historical value consists of a value, a quality, and a timestamp. A server can also let clients insert, replace, and delete values, attach annotations to values, and report the history of changes made to stored values.

A Thing Description [[WOT-THING-DESCRIPTION]] can describe OPC HDA items as WoT Properties that return a time series for a time range fixed in the Form, and as WoT Actions that accept the time range and other parameters as input. The Thing Description supplies the server, the item ID, the history method, and the parameters that an implementation needs.

The following topics are outside the initial scope:

  • the OPC XML-DA and OPC HDA XML web service specifications;
  • the IOPCHDA_Playback interface;
  • reading several items in one Form as a normative behavior;
  • server configuration, such as creating or deleting historized items; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the opchda scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the opchda URI scheme;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises;
  4. converts between OPC HDA times and [[RFC3339]] date-time values as specified; and
  5. delivers the quality of every historical value it returns.

The interoperable profile of this binding is the subset of its URI components, vocabulary terms, and behaviors that every conforming Consumer MUST support. A Thing Description that uses only the interoperable profile therefore works with every conforming Consumer, while anything outside it, such as a binding extension, is only understood by Consumers that implement that extension. Unless a section states otherwise, all URI components, vocabulary terms, and operation mappings defined normatively in this document belong to the interoperable profile.

OPC Classic Background

OPC Data Access (DA), OPC HDA, and OPC Alarms and Events (A&E) are known together as OPC Classic. They share the following foundations, which this binding relies on:

  • A server is a COM class, identified by a class identifier (CLSID) and usually also by a programmatic identifier (ProgID) such as Vendor.OPCHDAServer.1. A client creates the server object with CoCreateInstanceEx, on the local computer or, through DCOM, on a remote computer.
  • OPC HDA servers register themselves in the component category CATID_OPCHDAServer10. The OPC Server Enumerator (OPCEnum), installed with the OPC Core Components, lets a remote client list the registered servers and translate a ProgID into a CLSID through IOPCServerList2 [[OPC-COMMON]].
  • All OPC Classic servers implement IOPCCommon and announce an orderly shutdown through the IOPCShutdown callback interface [[OPC-COMMON]].
  • Callbacks, such as the delivery of newly historized values, are made over COM connection points, so the server calls back into the client process. Over DCOM this requires both computers to accept calls from each other.

In contrast to OPC DA, an OPC HDA client does not create groups. It obtains a server handle for each item ID with IOPCHDA_Server::GetItemHandles and passes the handles to the read and update methods.

URI Scheme and Addressing

Server URI

An OPC HDA server is identified by an opchda URI:

opchda-URI = "opchda://" host "/" server-id "/"
server-id  = progid / clsid

The components host, progid, and clsid, the resolution of a ProgID on a remote computer, and the prohibition of a port are defined exactly as for the opcda URI in [[WOT-OPCDA-BINDING]]. In particular, a Consumer MUST translate the ProgID of a remote server into a CLSID on the remote computer, the URI MUST NOT contain a port, and the base of a Thing Description MUST end with /. 

{
  "base": "opchda://historian.example.com/Vendor.OPCHDAServer.1/"
}

Item Reference

The resolved Form target identifies an item of the server:

opchda-item-URI = opchda-URI [ item-id ]

The item-id is the fully qualified item ID as defined by the server, for example Plant1.Unit3.FlowRate. It is a single path segment and is percent-encoded and decoded as specified for item IDs in [[WOT-OPCDA-BINDING]]: /, ?, #, %, [, ], \, and space MUST be percent-encoded, and a relative href whose item ID contains a colon MUST start with ./ or percent-encode the colon. An implementation MUST pass the percent-decoded item ID to the server exactly as written.

When the resolved target has no item-id, that is, when it equals the server URI, the Form addresses the server object itself, see Server Status. 

{
  "href": "Plant1.Unit3.FlowRate",
  "op": ["readproperty"],
  "opchdav:startTime": "NOW-1H"
}

OPC HDA Vocabulary

The examples use the prefix opchdav for the provisional namespace. The prefix intentionally differs from the opchda URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "opchdav": "https://www.w3.org/2026/wot/opchda"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Methods

The term opchdav:method selects the OPC HDA method that a Form invokes. The following values are defined. The third column lists the WoT operations for which the method is allowed, and the default method of each property operation is marked with an asterisk.

Value OPC HDA method Allowed WoT operations Result
ReadRaw IOPCHDA_SyncRead::ReadRaw readproperty*, invokeaction Time series of the stored values
ReadProcessed IOPCHDA_SyncRead::ReadProcessed readproperty, invokeaction Time series with one aggregate value per resample interval
ReadAtTime IOPCHDA_SyncRead::ReadAtTime invokeaction Time series with one value, interpolated when necessary, per requested timestamp
ReadModified IOPCHDA_SyncRead::ReadModified readproperty, invokeaction Modified values replaced or deleted in the time range
ReadAttribute IOPCHDA_SyncRead::ReadAttribute readproperty, invokeaction Attribute values in the time range
ReadAnnotations IOPCHDA_SyncAnnotations::Read readproperty, invokeaction Annotations in the time range
Insert IOPCHDA_SyncUpdate::Insert writeproperty, invokeaction None
Replace IOPCHDA_SyncUpdate::Replace writeproperty, invokeaction None
InsertReplace IOPCHDA_SyncUpdate::InsertReplace writeproperty*, invokeaction None
DeleteRaw IOPCHDA_SyncUpdate::DeleteRaw invokeaction None
DeleteAtTime IOPCHDA_SyncUpdate::DeleteAtTime invokeaction None
InsertAnnotations IOPCHDA_SyncAnnotations::Insert invokeaction None
AdviseRaw IOPCHDA_AsyncRead::AdviseRaw observeproperty*, unobserveproperty Time series of the values historized since the previous notification
AdviseProcessed IOPCHDA_AsyncRead::AdviseProcessed observeproperty, unobserveproperty Time series with the aggregate values of the completed resample intervals

A Form MUST only contain operations allowed for its method. Because the default method differs per operation, a Form without opchdav:method MAY combine readproperty, writeproperty, observeproperty, and unobserveproperty; each operation then uses its default method. A Form that carries opchdav:method applies that method to every operation of the Form. A Form containing invokeaction MUST carry opchdav:method.

Times

OPC HDA methods accept a time either as an absolute UTC time or as a string relative to the current time of the server. The terms opchdav:startTime and opchdav:endTime, and the time members of action inputs, accept both forms:

  • An absolute time is an [[RFC3339]] date-time, for example 2026-11-17T06:00:00Z.
  • A relative time follows the relative time syntax of [[OPC-HDA]]: a base keyword, optionally followed by one or more signed offsets, without white space. 
relative-time = keyword *offset
keyword       = "NOW" / "SECOND" / "MINUTE" / "HOUR" / "DAY" / "WEEK" / "MONTH" / "YEAR"
offset        = ( "+" / "-" ) 1*( 1*DIGIT unit )
unit          = "S" / "M" / "H" / "D" / "W" / "MO" / "Y"

NOW is the current time of the server. The other keywords denote the start of the current second, minute, hour, day, week, month, or year. The units denote seconds, minutes, hours, days, weeks, months, and years. For example, NOW-1H is one hour ago, and DAY-1D+7H30M is 07:30 yesterday.

A Consumer MUST pass a relative time to the server unchanged in the szTime member of OPCHDA_TIME, with bString set to TRUE, so that the server evaluates it. A Consumer MUST convert an absolute time to a UTC FILETIME and pass it in the ftTime member, with bString set to FALSE. A string that is neither an [[RFC3339]] date-time nor a relative time MUST be rejected.

When the start time is later than the end time, the server returns the values in reverse chronological order. Timestamps returned by the server are UTC FILETIME values and MUST be represented as [[RFC3339]] date-time values in UTC.

Aggregates

Processed methods compute one value per resample interval with an aggregate. The term opchdav:aggregate identifies the aggregate either by one of the following names or by its numeric identifier. Servers can offer vendor-specific aggregates, which are identified by number only and are listed by IOPCHDA_Server::GetAggregates.

Name Identifier OPC HDA aggregate
interpolative 1 OPCHDA_INTERPOLATIVE, the interpolated value at the start of the interval
total 2 OPCHDA_TOTAL, the time integral of the values
average 3 OPCHDA_AVERAGE, the average of the values
timeAverage 4 OPCHDA_TIMEAVERAGE, the time-weighted average
count 5 OPCHDA_COUNT, the number of raw values
standardDeviation 6 OPCHDA_STDEV
minimumActualTime 7 OPCHDA_MINIMUMACTUALTIME, the minimum, timestamped with its time of occurrence
minimum 8 OPCHDA_MINIMUM
maximumActualTime 9 OPCHDA_MAXIMUMACTUALTIME, the maximum, timestamped with its time of occurrence
maximum 10 OPCHDA_MAXIMUM
start 11 OPCHDA_START, the first value in the interval
end 12 OPCHDA_END, the last value in the interval
delta 13 OPCHDA_DELTA, the difference between the first and the last value
regressionSlope 14 OPCHDA_REGSLOPE
regressionConstant 15 OPCHDA_REGCONST
regressionDeviation 16 OPCHDA_REGDEV
variance 17 OPCHDA_VARIANCE
range 18 OPCHDA_RANGE, the difference between the maximum and the minimum
durationGood 19 OPCHDA_DURATIONGOOD, the duration of good quality, in seconds
durationBad 20 OPCHDA_DURATIONBAD, the duration of bad quality, in seconds
percentGood 21 OPCHDA_PERCENTGOOD
percentBad 22 OPCHDA_PERCENTBAD
worstQuality 23 OPCHDA_WORSTQUALITY
annotations 24 OPCHDA_ANNOTATIONS, the number of annotations

A Consumer MUST pass the numeric identifier of the aggregate to the server. A server that does not support the aggregate fails the request with OPC_E_INVALIDAGGREGATE, which the Consumer MUST report as an error.

Item Attributes

Every OPC HDA item has attributes that describe it and that can change over time. The term opchdav:attributeId selects the attribute read by ReadAttribute. The following identifiers are defined by [[OPC-HDA]]; servers can offer further, vendor-specific attributes, which are listed by IOPCHDA_Server::GetItemAttributes.

Identifier Attribute Typical use in a Thing Description
1 Data type opchdav:type and the Data Schema type of value
2 Description description
3 Engineering units unit
4 Stepped, that is, the value is not interpolated between raw values choice of aggregate
5 Archiving, that is, the server is currently collecting values applicability of AdviseRaw
6 to 10 Derive equation, node name, process name, source name, and source type documentation
11, 12 Normal maximum and normal minimum range of the item
13 Item ID href
14, 15 Maximum and minimum time interval between stored values opchdav:updateInterval and opchdav:resampleInterval
16 to 19 Exception deviation, exception deviation type, and high and low entry limits documentation

Operation Mappings

Item Handles

Before invoking a method for an item, the Consumer MUST obtain a server handle for the percent-decoded item ID with IOPCHDA_Server::GetItemHandles. A Consumer MAY cache the handle for later operations on the same item, and MUST release it with IOPCHDA_Server::ReleaseItemHandles when it no longer needs it. An unknown or invalid item ID fails the operation.

Property Mappings

WoT operation OPC HDA mapping Requirements
readproperty Call the method selected by opchdav:method, ReadRaw by default, with the time range given by opchdav:startTime and opchdav:endTime and the other parameters of the method taken from the Form, and convert the result. opchdav:startTime MUST be present.
writeproperty Convert the supplied time series and call the method selected by opchdav:method, InsertReplace by default, passing the item handle once for every value together with the value's timestamp, value, and quality. The server MUST support the method, as reported by IOPCHDA_SyncUpdate::QueryCapabilities, and the property MUST NOT be declared readOnly: true.
observeproperty Register an IOPCHDA_DataCallback through the server's IConnectionPointContainer and call the method selected by opchdav:method, AdviseRaw by default. AdviseRaw receives opchdav:startTime, or NOW when absent, and opchdav:updateInterval. AdviseProcessed receives opchdav:startTime, or NOW when absent, opchdav:resampleInterval, opchdav:aggregate, and opchdav:numIntervals. Every OnDataChange callback for the request is a notification whose data is a time series. observable SHOULD be true. The server MUST implement IOPCHDA_AsyncRead.
unobserveproperty Call IOPCHDA_AsyncRead::Cancel with the cancel identifier returned by the advise method. None.

A Form that carries ReadProcessed MUST also carry opchdav:aggregate, and a Form that carries ReadAttribute MUST also carry opchdav:attributeId, unless the Form only contains invokeaction and the action input supplies the parameter. A Form whose observeproperty operation uses AdviseRaw MUST carry opchdav:updateInterval, and one that uses AdviseProcessed MUST carry opchdav:aggregate and a positive opchdav:resampleInterval.

A readproperty operation with relative times returns a sliding window of history, for example the values of the last hour for "opchdav:startTime": "NOW-1H". A Thing Description that needs the application to choose the time range SHOULD use an Action instead.

Action Mappings

An invokeaction operation calls the method given by opchdav:method. The parameters of the method are taken from the Form terms and are overridden by members of the same name in the action input, which MUST be a JSON object when present. The following input members are defined:

Member Used by Value
startTime, endTime ReadRaw, ReadProcessed, ReadModified, ReadAttribute, ReadAnnotations, DeleteRaw string, as described in Times
numValues ReadRaw, ReadModified integer
bounds ReadRaw boolean
aggregate, resampleInterval ReadProcessed as the corresponding Form terms
attributeId ReadAttribute integer
timestamps ReadAtTime, DeleteAtTime array of [[RFC3339]] date-time strings
values Insert, Replace, InsertReplace time series
annotations InsertAnnotations array of objects with the members timestamp and annotation

The action output is the result listed in Methods. Update, delete, and annotation methods have no output. They pass the item handle once for every value, timestamp, or annotation, and the action fails when the server reports an error for any of them. OPC HDA has no transactions, so the values for which the server reported success remain changed; the Consumer SHOULD report which values failed.

Server Status

A Form whose resolved target equals the server URI addresses the server object. Such a Form MUST only contain the readproperty operation and MUST NOT carry opchdav:method. readproperty calls IOPCHDA_Server::GetHistorianStatus and returns an object with the following members:

Member Output parameter Value
state pwStatus One of up, down, and indeterminate, for OPCHDA_UP, OPCHDA_DOWN, and OPCHDA_INDETERMINATE
currentTime pftCurrentTime [[RFC3339]] date-time
startTime pftStartTime [[RFC3339]] date-time
version pwMajorVersion, pwMinorVersion, pwBuildNumber string of the form major.minor.build
maxReturnValues pdwMaxReturnValues integer; 0 means no limit
statusString ppszStatusString string
vendorInfo ppszVendorInfo string

Members whose output parameter the server does not provide MUST be omitted.

Server Shutdown

A Consumer SHOULD register an IOPCShutdown callback with the server [[OPC-COMMON]]. When the server calls ShutdownRequest, the Consumer MUST release all references to the server, MUST end all active observations with an error that includes the reason supplied by the server, and MAY reconnect later.

Event Mappings

No default mapping is defined for subscribeevent, unsubscribeevent, or WoT Event affordances. A Thing Description conforming to the profile MUST NOT advertise those operations on an opchda Form unless it also declares and documents an additional binding extension.

Error Handling

OPC HDA reports errors per item, value, or attribute as HRESULT codes. A Consumer MUST report a failed operation to the application when the call or a per-item result fails. The following codes are particularly relevant:

Code Meaning Consumer behavior
OPC_E_UNKNOWNITEMID, OPC_E_INVALIDITEMID The item ID is not known to the server or is syntactically invalid. Fail the operation.
OPC_S_NODATA The time range contains no data. Succeed with an empty time series.
OPC_S_MOREDATA The server returned fewer values than exist, because of numValues or its own limit. When numValues is 0, continue reading as described below, or report to the application that the result is incomplete. Otherwise, succeed.
OPC_E_MAXEXCEEDED The request exceeds the maximum number of values that the server can return. Fail the operation.
OPC_E_INVALIDAGGREGATE The aggregate is not supported for the item. Fail the operation.
OPC_E_INVALIDATTRID, OPC_E_UNKNOWNATTRID The attribute identifier is invalid or not known to the server. Fail the operation.
OPC_S_CURRENTVALUE The attribute has no history, and only its current value was returned. Succeed.
OPC_E_NOT_AVAIL The method is not available for the item. Fail the operation.
OPC_E_DATAEXISTS, OPC_E_NODATAEXISTS Insert found a value at the timestamp, or Replace or a delete method found none. Fail the operation.
OPC_E_INVALIDDATATYPE The written value has a data type that the server cannot store for the item. Fail the operation.
OPC_S_INSERTED, OPC_S_REPLACED InsertReplace inserted or replaced the value. Succeed.

To continue a ReadRaw or ReadModified after OPC_S_MOREDATA, the Consumer repeats the call with the start time set to the timestamp of the last returned value and drops values it has already returned, until the server no longer reports OPC_S_MOREDATA.

Payload Mapping

Time Series

Historical values are represented at the WoT Consumer boundary as a JSON array of objects, one per value, in the order returned by the server. Each object has the following members:

Member Description Value
timestamp Timestamp of the value. [[RFC3339]] date-time in UTC
value Value, converted from its VARIANT as described for OPC DA item values in [[WOT-OPCDA-BINDING]]. JSON value, or null when the server returned VT_EMPTY
quality OPC HDA quality. The low 16 bits carry the OPC DA quality, and the high 16 bits carry the OPC HDA quality flags, such as OPCHDA_RAW (0x40000), OPCHDA_INTERPOLATED (0x20000), OPCHDA_CALCULATED (0x80000), and OPCHDA_NODATA (0x200000). integer, from 0 to 4294967295

Because every value carries its quality, values of every quality are delivered and the application evaluates the quality. The WoT Data Schema of the affordance MUST describe this array, as shown in the Examples.

When writing, timestamp and value are required. When quality is absent, the Consumer MUST pass OPC_QUALITY_GOOD (192). When opchdav:type is present, the Consumer MUST convert every value to that type before passing it to the server. 

[
  { "timestamp": "2026-11-17T06:00:00Z", "value": 41.7, "quality": 262336 },
  { "timestamp": "2026-11-17T06:00:05Z", "value": 41.9, "quality": 262336 }
]

The quality 262336 is OPCHDA_RAW combined with OPC_QUALITY_GOOD.

Modified Values

ReadModified returns the values that were replaced or deleted, as a time series whose objects additionally have the following members:

Member Description Value
modificationTime Time at which the value was modified. [[RFC3339]] date-time in UTC
editType Kind of modification. One of insert, replace, insertReplace, and delete, for OPCHDA_INSERT to OPCHDA_DELETE
user User who made the modification. string

Attribute Values

ReadAttribute returns a JSON array of objects with the members timestamp and value, one for every value of the attribute in the time range. Attribute values carry no quality.

Annotations

ReadAnnotations returns a JSON array of objects with the members timestamp, the timestamp of the annotated value; annotation, the annotation text; annotationTime, the time at which the annotation was entered; and user, the user who entered it. For InsertAnnotations, only timestamp and annotation are supplied; the server sets the annotation time and the user.

Generating Thing Descriptions

OPC HDA servers are browsable. A tool that generates a Thing Description can walk the server address space with the IOPCHDA_Browser object returned by IOPCHDA_Server::CreateBrowse, and create a Property or an Action for every item, using the fully qualified item ID as the href. It can then read the current values of the item attributes with ReadAttribute to fill in the affordance:

  • the data type (1) gives the Data Schema type of value;
  • the description (2) and the engineering units (3) give description and unit;
  • a stepped item (4) is better summarized with timeAverage than with interpolative; and
  • IOPCHDA_SyncUpdate::QueryCapabilities and IOPCHDA_SyncAnnotations::QueryCapabilities tell whether update and annotation methods can be offered.

Security Considerations

OPC HDA relies on the security of COM and DCOM [[MS-DCOM]], exactly as OPC DA does. The security considerations of [[WOT-OPCDA-BINDING]] apply unchanged, in particular:

  • a Consumer SHOULD use the authentication level RPC_C_AUTHN_LEVEL_PKT_PRIVACY and MUST use at least RPC_C_AUTHN_LEVEL_PKT_INTEGRITY for remote servers [[KB5004442]];
  • a Consumer that observes properties accepts incoming DCOM calls, and SHOULD restrict them to the account of the server;
  • a Thing Description SHOULD describe an opchda endpoint with the auto security scheme of [[WOT-THING-DESCRIPTION]], and nosec MUST NOT be used for a remote server; and
  • servers can additionally implement the OPC Security interfaces [[OPC-SECURITY]].

Historical data is often used as a record for quality assurance and regulatory purposes. Update, delete, and annotation methods change that record. A Thing Description SHOULD only expose them where the application requires it, and a Consumer SHOULD treat such Forms as privileged operations. A server records the user of every modification, which ReadModified returns, so the Windows account of the Consumer becomes part of the record.

Unbounded reads, for example ReadRaw over many years with numValues set to 0, can put heavy load on the server and the Consumer. A Consumer SHOULD limit the number of values it accumulates when continuing reads after OPC_S_MOREDATA.

As in [[WOT-OPCDA-BINDING]], this binding does not yet define security scheme terms for selecting the DCOM authentication level and impersonation level, or for passing explicit Windows or OPC Security credentials.

Implementation Notes

  • OPC HDA uses COM and is therefore native to Microsoft Windows. Consumers on other platforms need a DCOM implementation of their own, or a gateway that exposes the server through another protocol, such as an OPC UA wrapper of an OPC HDA server.
  • Remote access requires the OPC proxy and stub libraries of the OPC Core Components on both computers, and the OPC Server Enumerator on the server computer for ProgID resolution.
  • Many products offer an OPC DA server and an OPC HDA server for the same item IDs. A Thing Description can then combine an opcda Form for the current value and an opchda Form for its history in the same Thing, using absolute href values for the Forms that do not match base.
  • The aggregates of OPC HDA were carried over into OPC UA Part 13, so the aggregate names of this binding remain recognizable when a historian is later accessed through OPC UA.

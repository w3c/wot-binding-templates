This Web of Things (WoT) protocol binding describes how a Thing Description exposes the items of an OPC Historical Data Access (OPC HDA) server [[OPC-HDA]], one of the COM-based OPC Classic specifications, and how the history of those items is made available through OPC UA Historical Access [[OPC-UA-PART11]].

The binding is limited to local COM: the Consumer and the OPC HDA server run on the same computer. Remote access through Distributed COM (DCOM) is not supported, see COM Only.

The binding defines:

  • the opchda URI scheme used to identify a local OPC HDA server and the items it historizes;
  • the representation of every historized item as a WoT Property whose value is the most recently historized value of the item, with its quality and timestamp delivered as metadata;
  • subscriptions to newly historized values;
  • the exposure of such a Property as a historizing OPC UA Variable, and the mapping of the OPC UA HistoryRead and HistoryUpdate services, aggregates, and annotations onto the OPC HDA interfaces; and
  • mappings between WoT operations and the OPC HDA interfaces.

This protocol binding is not an OPC Foundation specification.

This document is a work in progress.

This initial version of the binding covers the synchronous read, update, and annotation interfaces and the AdviseRaw operation of OPC HDA 1.20 servers through local COM; DCOM is not covered. It shares the URI layout, the COM-only scope, and the security considerations of the companion OPC DA Binding [[WOT-OPCDA-BINDING]] and OPC A&E Binding.

Introduction

OPC Historical Data Access is the OPC Classic specification for process historians. An OPC HDA server is a COM server that runs on a Microsoft Windows computer and gives clients access to the archived values of items, which it typically collects from OPC DA servers or directly from control systems. Clients on the same computer reach the server through COM. The OPC HDA specification also allows remote clients through Distributed COM (DCOM) [[MS-DCOM]], which this binding does not support.

Each item is identified by an item ID, a server-specific string such as Plant1.Unit3.FlowRate. A client reads the raw values stored for an item in a time range, or lets the server compute processed values, such as averages or minima, over consecutive resample intervals with an aggregate. Every historical value consists of a value, a quality, and a timestamp. A server can also let clients insert, replace, and delete values, attach annotations to values, and report the history of changes made to stored values.

A Thing Description [[WOT-THING-DESCRIPTION]] describes the current state of a Thing and has no standard way to describe time ranges, time series, or aggregates. This binding therefore describes every OPC HDA item as a WoT Property whose value is the most recently historized value of the item, in the same way as an item of an OPC DA server. The history of the item is accessed through OPC UA instead: a Consumer that exposes the Property as an OPC UA Variable, for example a WoT gateway that is also an OPC UA server, marks the Variable as historizing and maps the OPC UA Historical Access services [[OPC-UA-PART11]] onto the OPC HDA methods, as specified in OPC UA Historical Access. This keeps the Thing Description simple and gives OPC UA clients the same view of the history that OPC UA wrappers of OPC HDA servers provide.

The following topics are outside the initial scope:

  • remote access through DCOM, see COM Only;
  • the OPC XML-DA and OPC HDA XML web service specifications;
  • history access through WoT operations, such as Properties or Actions that return time series, and the AdviseProcessed and IOPCHDA_Playback subscriptions to processed or replayed values;
  • reading several items in one Form as a normative behavior;
  • server configuration, such as creating or deleting historized items; and
  • normative discovery behavior.

A Thing Description conforms to this binding when all Forms using the opchda scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the opchda URI scheme and rejects URIs that do not address the local computer;
  2. resolves relative Form href values against the Thing Description base URI;
  3. supports the operation mappings it advertises;
  4. handles the quality and timestamp of the values it returns as specified; and
  5. when it exposes Properties as OPC UA Variables, maps the OPC UA Historical Access services as specified in OPC UA Historical Access.

The interoperable profile of this binding is the subset of its URI components, vocabulary terms, and behaviors that every conforming Consumer MUST support. A Thing Description that uses only the interoperable profile therefore works with every conforming Consumer, while anything outside it, such as a binding extension, is only understood by Consumers that implement that extension. Unless a section states otherwise, all URI components, vocabulary terms, and operation mappings defined normatively in this document belong to the interoperable profile.

OPC Classic Background

OPC Data Access (DA), OPC HDA, and OPC Alarms and Events (A&E) are known together as OPC Classic. They share the following foundations, which this binding relies on:

  • A server is a COM class, identified by a class identifier (CLSID) and usually also by a programmatic identifier (ProgID) such as Vendor.OPCHDAServer.1. A client creates the server object with CoCreateInstance. Most OPC servers are out-of-process servers, that is, separate executables that COM starts on demand.
  • OPC HDA servers register themselves in the component category CATID_OPCHDAServer10, which lets a client list the OPC HDA servers installed on the computer.
  • All OPC Classic servers implement IOPCCommon and announce an orderly shutdown through the IOPCShutdown callback interface [[OPC-COMMON]].
  • Callbacks, such as the delivery of newly historized values, are made over COM connection points, so the server calls back into the client process.

In contrast to OPC DA, an OPC HDA client does not create groups. It obtains a server handle for each item ID with IOPCHDA_Server::GetItemHandles and passes the handles to the read and update methods.

COM Only

This binding only covers access to an OPC HDA server through local COM. The Consumer MUST run on the same computer as the server. Access to a server on another computer through DCOM [[MS-DCOM]] is outside the scope of this binding, and a Consumer MUST NOT use DCOM to realize an opchda Form.

This is a deliberate limitation, shared with the companion OPC DA and OPC A&E bindings. DCOM is generally not used in industry today because of its complex firewall and permission configuration and its security issues; remote access to OPC Classic servers is instead commonly provided by OPC UA wrappers or tunnelling products that run next to the server. The rationale is described in more detail in [[WOT-OPCDA-BINDING]].

A Thing Description that is consumed on another computer therefore describes the historian through such a gateway with a different protocol binding, or it is used by a Consumer, such as a WoT gateway, that runs on the server computer and exposes the history again through a network protocol, such as OPC UA.

URI Scheme and Addressing

Server URI

An OPC HDA server is identified by an opchda URI:

opchda-URI = "opchda://localhost/" server-id "/"
server-id  = progid / clsid

The host, which is always localhost, and the components progid and clsid are defined exactly as for the opcda URI in [[WOT-OPCDA-BINDING]]. In particular, a Consumer MUST reject an opchda URI with any other host, the URI MUST NOT contain a port, user information, query, or fragment, and the base of a Thing Description MUST end with /. 

{
  "base": "opchda://localhost/Vendor.OPCHDAServer.1/"
}

Item Reference

The resolved Form target identifies an item of the server:

opchda-item-URI = opchda-URI [ item-id ]

The item-id is the fully qualified item ID as defined by the server, for example Plant1.Unit3.FlowRate. It is a single path segment and is percent-encoded and decoded as specified for item IDs in [[WOT-OPCDA-BINDING]]: /, ?, #, %, [, ], \, and space MUST be percent-encoded, and a relative href whose item ID contains a colon MUST start with ./ or percent-encode the colon. An implementation MUST pass the percent-decoded item ID to the server exactly as written.

When the resolved target has no item-id, that is, when it equals the server URI, the Form addresses the server object itself, see Server Status. 

{
  "href": "Plant1.Unit3.FlowRate",
  "op": ["readproperty", "observeproperty", "unobserveproperty"],
  "opchdav:updateInterval": 10000
}

OPC HDA Vocabulary

The examples use the prefix opchdav for the provisional namespace. The prefix intentionally differs from the opchda URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "opchdav": "https://www.w3.org/2026/wot/opchda"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Form Terms

Vocabulary term Description Assignment Value
href Item reference, resolved against base when relative. required anyURI
op WoT operations supported by the Form: readproperty, observeproperty, and unobserveproperty. required string or Array of string
opchdav:updateInterval Interval, in milliseconds, at which the server delivers newly historized values to an observeproperty operation, see Property Mappings. required for observeproperty unsignedLong
opchdav:timeout Maximum time to wait for the server response, in milliseconds. optional unsignedInt

Operation Mappings

Item Handles

Before invoking a method for an item, the Consumer MUST obtain a server handle for the percent-decoded item ID with IOPCHDA_Server::GetItemHandles. A Consumer MAY cache the handle for later operations on the same item, and MUST release it with IOPCHDA_Server::ReleaseItemHandles when it no longer needs it. An unknown or invalid item ID fails the operation.

Property Mappings

WoT operation OPC HDA mapping Requirements
readproperty Call IOPCHDA_SyncRead::ReadRaw with an unspecified start time, the end time NOW, one value, and without bounding values, and convert the returned value. Because only the end time and the number of values are specified, the server reads backward from the current time and returns the most recently historized value. None.
observeproperty Register an IOPCHDA_DataCallback through the server's IConnectionPointContainer and call IOPCHDA_AsyncRead::AdviseRaw with the start time NOW and the update interval opchdav:updateInterval. Every value returned in an OnDataChange callback for the request is a separate notification, delivered in the chronological order of the values. observable SHOULD be true. The Form MUST carry opchdav:updateInterval, and the server MUST implement IOPCHDA_AsyncRead.
unobserveproperty Call IOPCHDA_AsyncRead::Cancel with the cancel identifier returned by AdviseRaw. None.

A Property that uses an opchda Form MUST be declared readOnly: true, and no mapping is defined for writeproperty. OPC HDA stores values together with their timestamps and has no notion of writing the current value of an item. Values are inserted, replaced, and deleted in the history through OPC UA HistoryUpdate, as described in HistoryUpdate.

A historian stores values after it has collected them, so the value returned by readproperty and the notifications of observeproperty can lag behind the current value of the underlying data source. An observeproperty operation delivers at most one batch of values per update interval.

Server Status

A Form whose resolved target equals the server URI addresses the server object. Such a Form MUST only contain the readproperty operation. readproperty calls IOPCHDA_Server::GetHistorianStatus and returns an object with the following members:

Member Output parameter Value
state pwStatus One of up, down, and indeterminate, for OPCHDA_UP, OPCHDA_DOWN, and OPCHDA_INDETERMINATE
currentTime pftCurrentTime [[RFC3339]] date-time
startTime pftStartTime [[RFC3339]] date-time
version pwMajorVersion, pwMinorVersion, pwBuildNumber string of the form major.minor.build
maxReturnValues pdwMaxReturnValues integer; 0 means no limit
statusString ppszStatusString string
vendorInfo ppszVendorInfo string

Members whose output parameter the server does not provide MUST be omitted.

Server Shutdown

A Consumer SHOULD register an IOPCShutdown callback with the server [[OPC-COMMON]]. When the server calls ShutdownRequest, the Consumer MUST release all references to the server, MUST end all active observations with an error that includes the reason supplied by the server, and MAY reconnect later.

Action and Event Mappings

No default mapping is defined for invokeaction, subscribeevent, or unsubscribeevent, or for WoT Action and Event affordances. A Thing Description conforming to the profile MUST NOT advertise those operations on an opchda Form unless it also declares and documents an additional binding extension. History reads and updates are made through OPC UA, see OPC UA Historical Access.

Error Handling

OPC HDA reports errors per item, value, or attribute as HRESULT codes. A Consumer MUST report a failed WoT operation to the application when the call or a per-item result fails. A Consumer that maps an OPC UA history service reports the result of every node or value as the OPC UA status code given in the following table, and as BadUnexpectedError for any other failure code.

Code Meaning WoT Consumer behavior OPC UA status code
OPC_E_UNKNOWNITEMID, OPC_E_INVALIDITEMID The item ID is not known to the server or is syntactically invalid. Fail the operation. BadNodeIdUnknown, BadNodeIdInvalid
OPC_S_NODATA The time range contains no data. Fail readproperty, because the item has no historized value yet. GoodNoData
OPC_S_MOREDATA The server returned fewer values than exist in the time range. Not applicable. Good, with a ContinuationPoint, see HistoryRead
OPC_E_MAXEXCEEDED The request exceeds the maximum number of values that the server can return. Fail the operation. Not returned; the Consumer limits each call to maxReturnValues and returns a ContinuationPoint
OPC_E_INVALIDAGGREGATE, OPC_E_NOT_AVAIL The aggregate or the method is not available for the item. Not applicable. BadAggregateNotSupported for processed reads, otherwise BadHistoryOperationUnsupported
OPC_E_INVALIDATTRID, OPC_E_UNKNOWNATTRID The attribute identifier is invalid or not known to the server. Not applicable. BadAttributeIdInvalid
OPC_E_DATAEXISTS Insert found a value at the timestamp. Not applicable. BadEntryExists
OPC_E_NODATAEXISTS Replace or a delete method found no value at the timestamp. Not applicable. BadNoEntryExists
OPC_E_INVALIDDATATYPE, OPC_E_BADTYPE, DISP_E_TYPEMISMATCH The value has a data type that the server cannot store or convert for the item. Fail the operation. BadTypeMismatch
OPC_E_RANGE, DISP_E_OVERFLOW The value is out of range. Not applicable. BadOutOfRange
OPC_E_BADRIGHTS, E_ACCESSDENIED The item is not writable, or the account of the Consumer is not authorized. Fail the operation. BadNotWritable, BadUserAccessDenied
OPC_S_INSERTED, OPC_S_REPLACED InsertReplace inserted or replaced the value. Not applicable. GoodEntryInserted, GoodEntryReplaced

Payload Mapping

Values

An item value is represented at the WoT Consumer boundary as the JSON value compatible with the Property's WoT Data Schema. The binding implementation converts the VARIANT returned by the server as described for OPC DA item values in [[WOT-OPCDA-BINDING]]. The data type attribute of the item, see Item Attributes, describes the type of the VARIANT.

Quality and Timestamp

OPC HDA returns every value together with a 32-bit quality and a UTC timestamp [[OPC-HDA]]. As in [[WOT-OPCDA-BINDING]], they are metadata of the value rather than part of the payload: the WoT Data Schema does not describe them, and a Consumer that makes them available to the application does so alongside the value, through implementation-specific means.

The low 16 bits of the quality carry the OPC DA quality, and the high 16 bits carry the OPC HDA quality flags. A Consumer that exposes the value through OPC UA, as the value of a Variable or in a history read result, MUST map the quality to an OPC UA status code [[OPC-UA-PART11]] as follows. The first matching row of the table applies; the historian flags of the last five rows are combined with the status code derived from the OPC DA quality as described in [[WOT-OPCDA-BINDING]].

OPC HDA quality flag OPC UA status code
OPCHDA_NOBOUND (0x00100000) BadBoundNotFound
OPCHDA_NODATA (0x00200000) BadNoData
OPCHDA_DATALOST (0x00400000) BadDataLost
OPCHDA_CONVERSION (0x00800000) BadTypeMismatch
OPCHDA_RAW (0x00040000) historian bits Raw
OPCHDA_CALCULATED (0x00080000) historian bits Calculated
OPCHDA_INTERPOLATED (0x00020000) historian bits Interpolated
OPCHDA_EXTRADATA (0x00010000) historian bit ExtraData
OPCHDA_PARTIAL (0x01000000) historian bit Partial

The timestamp is a UTC FILETIME. It MUST be represented as an [[RFC3339]] date-time in UTC at the WoT Consumer boundary and becomes the SourceTimestamp of the OPC UA value. The rules of [[WOT-OPCDA-BINDING]] for values with uncertain and bad quality apply unchanged to readproperty and observeproperty.

OPC UA Historical Access

This section applies to a Consumer that exposes Properties with opchda Forms as OPC UA Variables, for example a WoT gateway that is also an OPC UA server. It specifies how the Variable and its history are represented in OPC UA [[OPC-UA-PART11]] and how the OPC UA history services are mapped onto the OPC HDA interfaces of the item addressed by the Form.

Historizing Variables

For every such Property, the Consumer MUST expose an OPC UA Variable with:

  • a Value attribute whose value, status code, and SourceTimestamp are those returned by readproperty, see Quality and Timestamp;
  • a Historizing attribute that reflects the archiving attribute of the item;
  • an AccessLevel attribute with CurrentRead and HistoryRead, and with HistoryWrite when IOPCHDA_SyncUpdate::QueryCapabilities reports at least one update capability;
  • a HasHistoricalConfiguration reference to an HA Configuration Object of type HistoricalDataConfigurationType, whose Properties are taken from the item attributes; and
  • when the server implements IOPCHDA_SyncAnnotations, an Annotations Property with the data type Annotation and an AccessLevel with HistoryRead when the server reports OPCHDA_READANNOTATIONCAP, and with HistoryWrite when it reports OPCHDA_INSERTANNOTATIONCAP.

Item Attributes

Every OPC HDA item has attributes that describe it and that can change over time. They are read with IOPCHDA_SyncRead::ReadAttribute. The following attributes are defined by [[OPC-HDA]] and map to the following OPC UA attributes and Properties; servers can offer further, vendor-specific attributes, which are listed by IOPCHDA_Server::GetItemAttributes and MAY be exposed as server-specific Properties.

2 Description Description attribute description
3 Engineering units EngineeringUnits Property unit
4 Stepped, that is, the value is not interpolated between raw values Stepped Property of the HA Configuration None
5 Archiving, that is, the server is currently collecting values Historizing attribute observable
6 Derive equation Definition Property of the HA Configuration None
7 to 10 Node name, process name, source name, and source type None; MAY be exposed as server-specific Properties None
11, 12 Normal maximum and normal minimum EURange Property None
13 Item ID NodeId and BrowseName href

A Consumer MAY give the OPC UA Properties of attributes that have a history the HistoryRead access level, and map a HistoryRead with ReadRawModifiedDetails on such a Property onto ReadAttribute. An attribute for which the server returns OPC_S_CURRENTVALUE has no history.

Times

OPC HDA methods take times as OPCHDA_TIME structures. A Consumer MUST pass an OPC UA DateTime as a UTC FILETIME in the ftTime member, with bString set to FALSE. The value DateTime.MinValue, which OPC UA uses for a time that is not specified, MUST be passed with bString set to TRUE and an empty szTime, which OPC HDA uses for the same purpose. The relative time NOW used by the Property Mappings is passed in szTime with bString set to TRUE, so that the server evaluates it.

As in OPC UA, a time range in which the start time is later than the end time, or in which only the end time and the number of values are specified, returns the values in reverse chronological order.

HistoryRead

A Consumer MUST map the OPC UA HistoryRead service as follows:

OPC UA history read details Node OPC HDA method OPC UA result
ReadRawModifiedDetails, isReadModified FALSE Variable IOPCHDA_SyncRead::ReadRaw, with numValuesPerNode as the number of values and returnBounds as the bounds flag HistoryData
ReadRawModifiedDetails, isReadModified TRUE Variable IOPCHDA_SyncRead::ReadModified HistoryModifiedData, whose ModificationInfo carries the modification time, the user, and the edit type, where OPCHDA_INSERT, OPCHDA_REPLACE, OPCHDA_INSERTREPLACE, and OPCHDA_DELETE map to the HistoryUpdateType values Insert, Replace, Update, and Delete
ReadProcessedDetails Variable IOPCHDA_SyncRead::ReadProcessed, once for every requested aggregate, with the processingInterval as the resample interval, see Aggregates HistoryData
ReadAtTimeDetails Variable IOPCHDA_SyncRead::ReadAtTime, with reqTimes as the timestamps HistoryData
ReadRawModifiedDetails, isReadModified FALSE Annotations Property IOPCHDA_SyncAnnotations::Read HistoryData with one Annotation structure per annotation, holding the annotation text as message, the user, and the annotation time, and timestamped with the timestamp of the annotated value
ReadRawModifiedDetails, isReadModified FALSE Property of an item attribute IOPCHDA_SyncRead::ReadAttribute HistoryData
ReadEventDetails any None BadHistoryOperationUnsupported

OPC HDA has no counterpart to the aggregateConfiguration of ReadProcessedDetails or the useSimpleBounds flag of ReadAtTimeDetails; the server applies its own configuration. Values are converted as described in Payload Mapping.

When the server returns OPC_S_MOREDATA, or when the number of values would exceed the maxReturnValues of the server or of the Consumer, the Consumer returns the values received so far together with a ContinuationPoint. To continue, the Consumer repeats the call with the start time set to the timestamp of the last returned value and drops the values it has already returned.

HistoryUpdate

A Consumer MUST map the OPC UA HistoryUpdate service as follows:

OPC UA history update details Node OPC HDA method
UpdateDataDetails, performInsertReplace Insert Variable IOPCHDA_SyncUpdate::Insert
UpdateDataDetails, performInsertReplace Replace Variable IOPCHDA_SyncUpdate::Replace
UpdateDataDetails, performInsertReplace Update Variable IOPCHDA_SyncUpdate::InsertReplace
DeleteRawModifiedDetails, isDeleteModified FALSE Variable IOPCHDA_SyncUpdate::DeleteRaw
DeleteAtTimeDetails Variable IOPCHDA_SyncUpdate::DeleteAtTime
UpdateStructureDataDetails, performInsertReplace Insert Annotations Property IOPCHDA_SyncAnnotations::Insert

All other combinations, including isDeleteModified TRUE, the Remove update type, and event history updates, MUST be rejected with BadHistoryOperationUnsupported.

The Consumer passes the item handle once for every updated value together with the SourceTimestamp, the value, and the quality of the value. It derives the quality from the OPC UA status code with the inverse of the mapping in [[WOT-OPCDA-BINDING]], and passes OPC_QUALITY_GOOD (0xC0) for a Good status code. For an annotation, it passes the timestamp and the annotation message; the server sets the annotation time and the user. The result of every value is converted as described in Error Handling. OPC HDA has no transactions, so values for which the server reported success remain changed when others fail.

Generating Thing Descriptions

OPC HDA servers are browsable. A tool that generates a Thing Description can walk the server address space with the IOPCHDA_Browser object returned by IOPCHDA_Server::CreateBrowse, and create a read-only Property for every item, using the fully qualified item ID as the href. It can then read the current values of the item attributes with ReadAttribute to fill in the Property, as listed in Item Attributes:

  • the data type (1) gives the Data Schema type;
  • the description (2) and the engineering units (3) give description and unit;
  • an item that is archiving (5) can be declared observable, with an opchdav:updateInterval that is not shorter than its minimum time interval (15).

As in [[WOT-OPCDA-BINDING]], the normal maximum and minimum (11, 12) define a nominal range, and values outside that range are allowed. They should therefore not be mapped to minimum and maximum.

Security Considerations

OPC HDA relies on the security of local COM, exactly as OPC DA does. The security considerations of [[WOT-OPCDA-BINDING]] apply unchanged, in particular:

  • COM checks the launch, activation, and access permissions of the server against the Windows account of the Consumer process, and a Consumer SHOULD run under a dedicated account with only the permissions it needs;
  • a Consumer that observes properties accepts incoming COM calls from the server process, and SHOULD restrict them to the account of the server;
  • a Thing Description SHOULD describe an opchda endpoint with the nosec security scheme of [[WOT-THING-DESCRIPTION]], because the Consumer supplies no security information, while the operating system and the server still enforce their permissions;
  • a Consumer that exposes the history to other computers, for example through OPC UA, becomes responsible for authenticating and authorizing remote clients; and
  • servers can additionally implement the OPC Security interfaces [[OPC-SECURITY]].

Historical data is often used as a record for quality assurance and regulatory purposes. OPC UA HistoryUpdate changes that record. A Consumer SHOULD only grant HistoryWrite to OPC UA users that are authorized to change it. The OPC HDA server records the Windows account of the Consumer as the user of every modification, whichever OPC UA user requested it, so a Consumer SHOULD keep its own audit trail, for example with the OPC UA audit events for history updates.

Unbounded history reads, for example raw reads over many years, can put heavy load on the server and the Consumer. A Consumer SHOULD limit the number of values it returns per HistoryRead call and use continuation points.

As in [[WOT-OPCDA-BINDING]], this binding does not yet define security scheme terms for passing OPC Security credentials.

readproperty on FlowRate returns the most recently historized flow rate, and observeproperty delivers the newly historized values every ten seconds.

History Read through OPC UA

A WoT gateway that consumes the Thing Description above and exposes FlowRate as a historizing OPC UA Variable receives a HistoryRead for the hourly time-weighted average of the previous day: 

ReadProcessedDetails
  startTime          = 2026-11-16T00:00:00Z
  endTime            = 2026-11-17T00:00:00Z
  processingInterval = 3600000
  aggregateType      = [ TimeAverage ]

The gateway obtains a handle for Plant1.Unit3.FlowRate and calls IOPCHDA_SyncRead::ReadProcessed with the two times as absolute FILETIME values, a resample interval of one hour, and the aggregate OPCHDA_TIMEAVERAGE. It returns the 24 values as HistoryData, whose status codes carry the historian bits Calculated or Interpolated reported by the server.

Implementation Notes

  • OPC HDA uses COM and is therefore native to Microsoft Windows. A Consumer implementing this binding runs on the Windows computer of the server. Consumers on other computers or platforms access the server through a gateway that exposes it through another protocol, typically OPC UA as described in OPC UA Historical Access.
  • Out-of-process servers require the OPC proxy and stub libraries of the OPC Core Components, so that the OPC interfaces can be marshalled between the Consumer and the server process.
  • Many products offer an OPC DA server and an OPC HDA server for the same item IDs. A gateway can then expose a single OPC UA Variable whose current value comes from the opcda Form of a Property and whose history comes from the opchda mapping of this binding, using absolute href values for the Forms that do not match base.
  • The mappings of quality codes, aggregates, and history services in this binding follow those of the OPC UA COM wrappers published by the OPC Foundation, so that OPC UA clients see the same history whether a historian is accessed through such a wrapper or through a WoT gateway. OPC UA Part 13 [[OPC-UA-PART13]] refined the definitions of several aggregates, so results computed by an OPC HDA server can differ slightly from those of a native OPC UA server.

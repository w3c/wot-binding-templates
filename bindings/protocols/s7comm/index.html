This initial version of the binding focuses exclusively on variable data access, that is, reading and writing individual memory locations of Siemens SIMATIC S7 controllers with the S7Comm protocol carried over ISO-on-TCP [[RFC1006]]. It follows the two open implementations surveyed for it, the Siemens driver of the OPC Foundation UA Edge Translator [[UA-EDGETRANSLATOR-S7]] and the S7 driver of Apache PLC4X [[PLC4X-S7]]. Alarm and event services, cyclic push subscriptions, and diagnostics are expected to be covered by future versions.

This Web of Things (WoT) protocol binding provides guidance for describing assets that are accessed with the Siemens S7Comm protocol, covering the S7-300, S7-400, S7-1200, and S7-1500 controller families as well as the S7-200 and LOGO! devices through a small set of connection conventions.

The binding defines:

  • the s7 URI scheme used to identify a controller, including rack and slot;
  • the controller family and the connection parameters a Consumer needs before it can address a variable;
  • memory-area addressing in WoT Forms, both as a TIA Portal-style address and as explicit Form terms;
  • the S7 data types and their encoding;
  • polling behavior, timeouts, and linear value conversion for observed properties; and
  • mappings between WoT property operations and S7 read and write services.

This protocol binding is not a Siemens specification.

This document is a work in progress.

Introduction

S7Comm is the protocol that Siemens SIMATIC S7 controllers use for programming and data access. It is carried by the ISO Transport Service on top of TCP [[RFC1006]], commonly called ISO-on-TCP or COTP, on TCP port 102. A client addresses a value by naming a memory area of the controller, a byte offset inside that area, and, for single bits, a bit offset, together with the data type needed to encode or decode the value.

Unlike controllers that expose named tags, an S7 controller does not usually publish its symbol table over S7Comm. The address is therefore taken from the engineering project, most commonly by copying the address out of TIA Portal or STEP 7. A Thing Description [[WOT-THING-DESCRIPTION]] carries that address, the data type, and the connection parameters, which is exactly the information a Consumer cannot obtain from the device itself.

The following topics are outside the initial scope:

  • alarm and event services, including ALARM_S and ALARM_8;
  • cyclic (CYC) push subscriptions;
  • SZL/SSL diagnostics and controller status (RUN/STOP) events;
  • the S7CommPlus protocol variant used for optimized blocks of the S7-1200 and S7-1500 families;
  • block upload, download, or any modification of the controller program;
  • PROFINET DCP discovery; and
  • symbol table upload.

A Thing Description conforms to this binding when all Forms using the s7 scheme follow the normative requirements in this document.

An implementation conforms to this binding when it:

  1. recognizes the s7 URI scheme;
  2. resolves relative Form href values against the Thing Description base URI;
  3. uses the rack and slot of the endpoint URI to establish the connection;
  4. supports the operation mappings it advertises; and
  5. interprets the declared S7 data type correctly.

The polling interval uses the unprefixed Form member pollingTime and Consumers implementing this binding MUST accept that name.

URI Scheme and Addressing

Endpoint URI

An S7 endpoint is identified by an s7 URI:

s7-URI = "s7://" host [ ":" port ] [ "/" rack "," slot ] [ "/" ]

Where:

  • host is an IPv4 address, IPv6 literal, or DNS name of the controller or of the communication processor in front of it;
  • port is optional; when omitted, an implementation uses the ISO-on-TCP port 102 [[RFC1006]]. Authors SHOULD omit it, because most S7 stacks do not allow the port to be changed;
  • rack and slot identify the CPU within the addressed station. When they are omitted, an implementation MUST assume rack 0 and slot 1.

Rack and slot are part of the interoperable profile because a connection cannot be established without them, and because their correct values differ per controller family: a CPU of an S7-1200 or S7-1500 is commonly reached at rack 0, slot 1, while an S7-300 or S7-400 CPU is commonly reached at rack 0, slot 2 and can sit in any other slot of its rack. A Thing Description that omits them is not portable between Consumers.

Endpoint Meaning
s7://192.168.0.10/0,1 CPU in rack 0, slot 1, typical for S7-1200 and S7-1500
s7://192.168.0.10/0,2 CPU in rack 0, slot 2, typical for S7-300 and S7-400
s7://192.168.0.10/1,3 CPU in rack 1, slot 3, reached through the communication processor at the given address

A Thing Description SHOULD place the endpoint, including rack and slot, in base and use relative addresses in individual Forms. Such a base MUST end with /; otherwise reference resolution [[RFC3986]] replaces the rack and slot with the address. 

{
  "base": "s7://192.168.0.10/0,1/",
  "s7v:controller": "S7_1500"
}

Controller Family

The S7 families differ in the data types they support, in the memory areas they expose, and in the way a connection is established. Some devices, in particular the S7-200, the S7-200 Smart, and LOGO!, do not answer the identification request that implementations use to detect the family, so the family has to be stated in the Thing Description.

A Thing Description carrying s7 Forms SHOULD declare the controller family at the top level with s7v:controller. When the term is absent, an implementation MAY detect the family from the device. The value is one of ANY, S7_200, S7_200_SMART, S7_300, S7_400, S7_1200, S7_1500, or LOGO.

The S7-200, the S7-200 Smart, and LOGO! additionally require explicit Transport Service Access Points instead of rack and slot addressing. A Thing Description for those devices MUST declare s7v:localTsap and s7v:remoteTsap. The TSAPs are connection configuration values of the individual device, not constants of the family, and authors MUST take them from the device configuration; a Consumer MUST NOT substitute a default. For example, 0x0200 (512) for both TSAPs is a common configuration of an S7-200, and LOGO! devices commonly use different local and remote values. When a non-zero TSAP is given, it overrides the rack and slot of the endpoint URI.

On an S7-200 the V variable memory of the Siemens tooling, such as VW310, is an alias for data block 1, so VW310 is addressed as %DB1.DBW310:INT in this binding.

Variable Address

The resolved Form target identifies one variable in the controller memory:

s7-address-URI = s7-URI "/" address
address        = "%" memory-area byte-offset [ "." bit-offset ] ":" data-type
               / "%DB" db-number "." "DB" short-code byte-offset [ "." bit-offset ] ":" data-type
               / "%DB" db-number ":" byte-offset [ "." bit-offset ] ":" data-type
data-type      = type-name [ "(" length ")" ]
short-code     = "X" / "B" / "W" / "D"

The address is the address notation of the Siemens engineering tools, so that it can be copied from TIA Portal, and it is the notation that the surveyed implementations parse [[PLC4X-S7]]. The third alternative is the short data block notation, which is handled identically to the second. The optional length declares the maximum length of a STRING or WSTRING value. Because the percent sign is reserved in URIs, it MUST be percent-encoded as %25, see Reserved Characters.

Address Meaning
%I0.3:BOOL Bit 3 of input byte 0
%Q1.0:BOOL Bit 0 of output byte 1
%M100:DINT 32-bit signed integer at flag or marker byte 100
%DB1.DBX0.3:BOOL Bit 3 of byte 0 of data block 1
%DB1.DBW20:INT 16-bit signed integer at byte 20 of data block 1
%DB5:10:INT The same shape in the short data block notation
%DB1.DBB0:STRING(80) String of up to 80 characters at byte 0 of data block 1

A Form addresses a single value. Reading a range of elements with one Form, such as %DB1.DBB0[0..9]:BYTE in [[PLC4X-S7]], is out of scope for this version of the binding. 

{
  "href": "./%25DB1.DBW20:INT"
}

When the Thing Description contains "base": "s7://192.168.0.10/0,1/", the resolved target is s7://192.168.0.10/0,1/%25DB1.DBW20:INT.

Explicit Address Terms

A Form MAY instead describe the address with the explicit terms s7v:area, s7v:dbNumber, s7v:byteOffset, s7v:bitOffset, and s7v:length. This is the shape that the UA Edge Translator driver consumes [[UA-EDGETRANSLATOR-S7]], and it avoids parsing a Siemens-specific string in Consumers that generate Thing Descriptions from an engineering export.

When the explicit terms are present, they take precedence over the address in href, and the href then only identifies the Form target. A Consumer MUST reject a Form in which both forms of addressing are present and describe different locations. Every Form MUST carry at least one of the two. 

{
  "href": "TankLevel",
  "op": ["readproperty"],
  "type": "s7v:INT",
  "s7v:area": "DB",
  "s7v:dbNumber": 1,
  "s7v:byteOffset": 20
}

Reserved Characters

S7 addresses contain characters that are reserved in URIs [[RFC3986]]. Authors MUST percent-encode them, in particular % as %25, [ as %5B, ] as %5D, ? as %3F, and # as %23. Because the address is a single path segment, / MUST be percent-encoded as %2F.

Every address contains a colon before the data type. A colon is not allowed in the first segment of a relative reference [[RFC3986]], so a relative href carrying an address MUST start with ./, as in ./%25DB1.DBW20:INT. Absolute s7 URIs need no prefix, because the address is then a non-initial path segment in which :, ., ,, (, and ) are allowed without encoding.

Reference resolution removes the leading ./. An implementation MUST percent-decode the address of the resolved URI before it is used. 

s7://192.168.0.10/0,1/%25DB1.DBX0.3:BOOL

S7Comm Vocabulary

The examples use the prefix s7v for the provisional namespace. The prefix intentionally differs from the s7 URI scheme name so that vocabulary terms are not confused with the scheme. 

{
  "s7v": "https://www.w3.org/2026/wot/s7comm"
}

The namespace URI is provisional. It does not imply that a vocabulary is published at that location.

Memory Areas

The memory area determines which part of the controller memory the byte offset refers to. Not every family exposes every area.

An implementation MUST reject an address whose memory area it does not support rather than reading a different area.

All multi-byte values are transferred in big-endian byte order, which is the byte order of the S7 controller families. A s7v:BOOL value is read and written as a single bit and therefore needs a bit offset, either in the address or in s7v:bitOffset.

A s7v:STRING value starts with two bytes that hold the declared maximum length and the current length, followed by the characters. An implementation MUST use the current length when decoding and MUST set it when encoding, and MUST NOT write more characters than the declared maximum length. A s7v:WSTRING value uses the same layout with two words instead of two bytes and two bytes per character.

Implementations MUST reject an unsupported type rather than silently decode it as another type.

Value Conversion

S7 programs frequently keep scaled integers, for example a temperature in tenths of a degree in an s7v:INT variable, or a raw analog value between 0 and 27648. A Form MAY therefore carry s7v:scale and s7v:offset. The value of s7v:scale MUST NOT be zero, because a zero factor loses the raw value on reads and makes the inverse conversion on writes undefined; a Consumer MUST reject a Form with a zero s7v:scale.

When reading, a Consumer computes the application-facing value as value = raw × s7v:scale + s7v:offset, and when writing it applies the inverse, raw = (value − s7v:offset) / s7v:scale, rounding to the nearest representable value of the declared type. These are the same two terms, with the same semantics, as in the Modbus and EtherNet/IP bindings, so that an author learns one rule for all three. 

{
  "href": "./%25IW64:INT",
  "op": ["readproperty"],
  "type": "s7v:INT",
  "s7v:scale": 0.0036169,
  "s7v:offset": -50
}

Operation Mappings

Default Mappings

WoT operation S7Comm behavior Requirements
readproperty Send an S7 Read Variable request for the addressed memory area, byte offset, and length, and decode the returned bytes according to type. The Form MUST identify a readable area.
writeproperty Encode the supplied value according to type and send it with an S7 Write Variable request. A s7v:BOOL value is written as a single bit, so that the neighboring bits of the byte are not affected. The property MUST NOT be declared readOnly: true.
observeproperty Repeatedly read the variable and notify the Consumer when a sample is available or its value changes, according to implementation behavior. observable SHOULD be true; pollingTime controls the requested interval.

This version of the binding does not use the cyclic push service of the S7-300 and S7-400 families, which is not available on the S7-1200 and S7-1500 families [[PLC4X-S7]]. An implementation realizes observeproperty by polling, SHOULD use pollingTime when supplied, and MAY enforce a minimum interval to protect the controller and network.

An implementation MAY combine the reads of several Forms of the same endpoint into a single request, as long as the request stays within the negotiated PDU size. Values larger than the PDU size MUST be transferred in several requests.

Action and Event Mappings

No default mapping is defined for:

  • invokeaction;
  • subscribeevent;
  • unsubscribeevent; or
  • WoT Event affordances.

A Thing Description conforming to this binding MUST NOT advertise those operations on an s7 Form unless it also declares and documents an additional binding extension. The alarm services of the S7-300 and S7-400 families are the natural basis for a future Event mapping.

Payload Mapping

Values are represented at the WoT Consumer boundary as the JSON value compatible with the Property's WoT Data Schema. The binding implementation converts between that value and the S7 wire representation, applying Value Conversion when it is declared.

A Consumer MUST use both the WoT Data Schema and the Form's S7 type. The WoT Data Schema describes the application-facing value, while the Form term identifies the controller representation.

This version of the binding does not describe the layout of a user-defined structure inside a data block. A structured value is described by one Form per member, each addressing its own byte offset, which is the access method that both surveyed implementations support.

Security Considerations

S7Comm, as used by this binding, provides no authentication, no authorization, and no confidentiality. A request carries no credential, and the payload travels in clear text over ISO-on-TCP. Any station that can reach TCP port 102 of the controller can read and write the memory areas that the controller exposes.

Controllers offer protection mechanisms outside the protocol data exchange. S7-300 and S7-400 CPUs support protection levels with a password that can make the CPU read-only or block access entirely. S7-1200 and S7-1500 CPUs add configurable access levels, the option to disable the PUT/GET communication that this binding relies on, and, on recent firmware, encrypted communication for the engineering connection. These are configured in the engineering project, not in the Thing Description.

A Thing Description MUST accurately describe the security applied to the interaction endpoint. Because the protocol itself carries no credential, a Thing Description for a plain S7Comm endpoint uses the nosec security scheme. A binding implementation MUST NOT infer that nosec authorizes access; controllers are expected to be operated on a protected network segment, and authorization remains a deployment responsibility.

Implementation Notes

This binding was derived from two open-source implementations.

The Siemens driver of the OPC Foundation UA Edge Translator [[UA-EDGETRANSLATOR-S7]] currently:

  • connects over ISO-on-TCP with a fixed port 102 and an explicit rack and slot, defaulting to rack 0, slot 1;
  • describes a variable with the Form members s7:target, s7:dbnumber, s7:start, s7:pos, s7:size, and s7:maxlen, which correspond to s7v:area, s7v:dbNumber, s7v:byteOffset, s7v:bitOffset, and s7v:length of this binding;
  • uses the area codes DB, MB, EB, AB, TM, and CT, which correspond to DB, M, I, Q, T, and C;
  • carries the canonical Siemens type name in s7:s7type, with the same set of names that this binding uses in type; and
  • reads a BOOL as a single bit at the absolute bit address, and every other type byte-wise.

The S7 driver of Apache PLC4X [[PLC4X-S7]] currently:

  • uses the connection string s7://{host}?{options}, with cotp.remote-rack, cotp.remote-slot, cotp.local-tsap, cotp.remote-tsap, controller-type, pdu-size, and read-timeout-ms among the options, all of which this binding expresses in the endpoint URI or in the vocabulary;
  • addresses variables with the TIA Portal notation that this binding adopts for href;
  • supports reading ranges of elements, which this binding leaves out of scope; and
  • supports cyclic and alarm subscriptions and memory-area browsing on the S7-300 and S7-400 families, which this binding leaves out of scope.

Both implementations use the s7 prefix for their vocabulary terms. This binding uses s7v so that the terms are not confused with the s7 URI scheme.
